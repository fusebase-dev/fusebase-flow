# Maintaining this repository

This is the maintainer process for `fusebase-dev/fusebase-flow`, approved on 2026-09-07. It overrides generic lifecycle ceremony for work on this framework. Consumer projects retain their own Flow workflow. Installation does not copy this file by default; `--with-framework-docs` places it under `docs/_fusebase-flow/` for reference.

## One outcome, one implementation pass

1. Record the intended outcome, affected boundary and a success/failure example in one issue or change note. Use a design document only when behavior or ownership needs a real decision. The same record owns the task list and results; no automatic spec/decisions/tasks/gate/handoff bundle.
2. Diagnose and implement with one owner. Review findings are direct work input: act on them and record only the choices they leave open; never derive a separate planning relay that restates them. Existing operator authorization carries forward within the approved work; an operator exception to this procedure (for example a pre-tag hosted run) covers only the release it was granted for and is asked again for the next. Role changes within the approved work do not require a new session or relay. Resolve factual unknowns through bounded read-only diagnosis; before implementing, apply `flow-skills/zoom-out/references/karpathy-guidelines.md` §1 to remaining uncertainty. Preserve existing authorization and ask about any external action not already authorized. One writer per worktree; parallel writers use separate worktrees. The integration owner checks the combined diff before release.
3. Choose the smallest meaningful test boundary using `docs/maintainer-testing.md`. Select checks by what the change can break, not by which groups read the changed file: a comment-only edit (the diff touches only comment lines — `#` outside heredocs and strings) needs its syntax check and any structural check over those lines, not the script's runtime groups; an edit to printed text also runs the groups that match the old text (`grep -rl '<old text>' hooks/tests`). A deterministic reproduction with a causal explanation is enough to fix; when the code itself shows the mechanism of a known failure class, that is the causal explanation. Repeat trials only investigate a race, flake or performance question whose mechanism the code does not already show; they declare a time bound first and never run on a contended host. No mandatory baseline full suite or three-run ritual. Before verification, name in chat — the operator reads chat, not the outcome record — the selected groups, what each can catch in this change, platform gaps and expected duration (the last hosted `END tag … elapsed` figures, scaled for the local host); for any wait over ten minutes say what runs, when it should finish and what follows. A group that can catch nothing in this change is not selected; expansion must name the uncovered boundary (for a local full run, as `FF_EVIDENCE_GAP`).
4. Review the diff once it is settled, concurrently with focused checks: a read-only review that runs no tests never waits behind a check (a review that runs its own reproductions does not share the host with a local run expected over ten minutes), and both results are reconciled before commit and before expensive verification. When the scope or the contract itself is undecided, review that premise before writing code, and where the scope is contested ask that review for the minimal plan at the observed cadence and what to cut first. Ordinary maintenance uses implementer review. Changes to ownership, upgrade/recovery authority, security or release publication require an independent review of the relevant contract and diff.
5. Resolve substantive findings together, classifying each before correcting it: does this finding expose a pre-existing mechanism, or a defect introduced by our previous correction? Does the correction preserve the contract across the whole affected path? Two consecutive "introduced" answers mean the approach is wrong rather than the instance; settle that contract instead of patching it again (`docs/problem-catalog/adversarial-review-convergence/problem.md`). Before editing, record in the existing outcome record only the unresolved choices and their counterexamples; cover missing evidence, partial failure, mixed outcomes and untrusted input where they apply. Link a correction to its finding instead of restating it, and supersede an instruction the work has overtaken. Re-review the corrections and affected boundaries, expanding only for a concrete new risk, and check the declared round bound before launching another round: exhaustion returns the unresolved work for a budget or scope decision and never makes a blocker shippable. The actor that declared the bound does not author its own extension — the operator may revise their own bound explicitly, an agent may not extend one silently — and a bound that exists only in chat cannot be checked before dispatch. Findings require an input/trigger, wrong outcome and expected behavior. Wording and unrelated improvements do not restart the gate unless they change behavior or a material public claim.
6. Commit one independently reversible outcome at a time; FR-03 here means that outcome with its fix, regression tests and required docs, never one finding, correction or artifact per commit. Unrelated outcomes stay separate. A probe, fixture calibration or report correction does not need its own task. Stamp affected manifests once those inputs settle, before committing or checking that snapshot; deferring a stamp past a committed snapshot leaves it inconsistent. Once behavior is demonstrated, applicable checks pass and blockers are resolved, finish.

If the same defect appears in another caller, inspect the entire caller family and settle its shared contract before another patch, version or tag. A known correctness or safety blocker never becomes acceptable because a review has already run once. Prior examples: `docs/problem-catalog/undecided-contract-drives-repeat-defects/problem.md`.

## Checks and evidence

| Stage | Required work |
|---|---|
| Edit loop | Affected tests and relevant syntax/configuration checks; `FF_ONLY=tag1,tag2 bash hooks/tests/run-tests.sh` when the registered runner is useful |
| Commit | Normal staged secret, protected-path, module-size and configured lint/typecheck checks; no mandatory separate validator invocation immediately before pre-commit |
| Maintainer CI | Focused deterministic contracts or the tags a manual dispatch names in `groups` on Linux and Windows/MSYS; feedback only, not release evidence |
| Release | Explicit essential profile and package integrity through `.github/workflows/fusebase-flow-verify.yml` on the exact tagged SHA; both platforms must succeed |
| Diagnostics | Editorial instruction checks, profiling and repeated performance experiments explicitly selected when their subject changes |

Configured validators execute normally; no signed-receipt shortcut is required. An earlier manual validator run is optional feedback. CI repeats checks because it supplies a clean independent environment. If a check is not configured, report that fact rather than inventing a lint/typecheck result.

Two-platform gating is mandatory: `verify-linux` and `verify-windows-msys`, plus the aggregate gate, must pass before publication. A focused CI/local pass is not release evidence. `PUBLISHING.md` owns release procedures. Essential-profile membership and diagnostic access are documented in `docs/maintainer-testing.md`.

Do not run an unchanged full pre-tag suite and then repeat the same tree in the mandatory tagged gate. That includes a local `FF_RELEASE`/`FF_FULL` run and a hosted `fusebase-flow-verify` dispatch on the release commit: each repeats the tagged gate on a slower or identical runner and delays publication by its full duration. Use focused pre-tag evidence; the exact tagged gate owns release verification. If the tagged gate then fails, follow Failure handling: a red tag is never moved; it turns green only through a re-run `PUBLISHING.md` allows (a transient environment failure, or the single pre-existing-intermittent re-run); otherwise the fix ships as the next version.

Record only commit/source state, selected command/group, environment, result and log pointer. Save large tool output to a local log and return its summary plus path; never place multi-megabyte logs in tool arguments. CI logs and existing reports own the detail. Repair a missing report field from valid evidence already present; never rerun an expensive check solely to populate prose. Verifying another agent's evidence means checking source/environment identity, raw results and oracle coverage; rerun only the smallest check that answers a mismatch, missing or unreliable evidence, an untested boundary or a disputed claim, and never replay valid same-source evidence merely because someone else produced it. The tagged release gate is never such a replay and stays required. A focused result can close the affected local task without pretending it was a complete suite. Save a handoff only when work must cross sessions.

After the exact-SHA gate, remote tag identity and publication are confirmed, finish with one factual documentation commit. A docs-only release closeout or maintainer-prose correction does not require a new tag or runtime suite; normal commit hooks apply, plus the relevant structural check only when machine-consumed markers change.

## Failure handling

| Observation | Action |
|---|---|
| Essential consumer behavior or runner-trust control fails | Resolve the blocker and rerun the affected owner before preparing the tagged release gate |
| Unrelated diagnostic or tooling check fails | Retain the evidence and open a separate follow-up; do not expand the release scope unless it invalidates an essential-profile result or runner trust |
| Wrong product behavior | Fix it and rerun affected tests |
| Proven fixture or tooling error | Fix the smallest responsible boundary and retain the original failure |
| Timeout, crash or zero result rows | Failed/incomplete execution; diagnose before retrying; never infer PASS from partial output |
| Same experiment without new inputs | Stop repeating it; choose a simpler oracle or resolve the prerequisite |
| Local group far slower than its hosted duration on a contended host but still producing rows (PASS/FAIL or `END tag` lines advancing), even up to its wall | Timing is not evidence: record it and never rerun it on the same host; an already-green hosted run of the same source, or the tagged gate, answers that group; a FAIL row it produced still goes to its own row. A phase that stops producing rows is the Timeout row |
| Tagged gate fails in a check that is not a runner-trust control, and `git diff --quiet <last published tag> <sha> -- <failing test> <files it sources or invokes>` succeeds | Pre-existing intermittent failure; for this release this row overrides the essential-failure and tooling-error rows. Keep the log, file or reopen its backlog item, and give the operator the choice with its cost: re-run the failed jobs of the same release run once, or fix it and ship the next version. A second failure blocks |
| Interrupted process tree | Inspect and clean only verified owned descendants before another run |
| Unrelated review suggestion | Record as optional follow-up; keep the current outcome fixed |

Use bounded execution and durable logs for long checks. Time budgets are design targets, not correctness assertions. Fix slow setup, isolation and repeated subprocesses before changing a wall; no blanket timeout increase or successful-prefix replay. No new instrumentation subsystem is needed to measure existing CI duration.
Reruns require a corrected input, implementation, or environment, apart from the single re-run the pre-existing-intermittent row allows; there is no other retry allowance. Before a local run expected to exceed ten minutes, check host load; on a contended Windows/MSYS host (other sessions, sustained CPU above about 50%) local wall-clock runs from several to tens of times the hosted figure and is not evidence, so leave heavy groups to hosted CI. If execution exceeds its estimate, report elapsed time, completed work, remaining checks and the blocker before expanding or restarting it. Example of what this section prevents: `docs/changes/2026-10-13-v510-time-review.md`.

## Safety and scope

Preserve user/CLI ownership, supported upgrade paths, prior activation intent, recoverability, secret/protected-path enforcement and truthful partial/failure states. Keep tag/verified-SHA binding and the publication dependency on verification. Do not bypass Git hooks, rewrite published tags or interpret local verification as permission to publish.

Apply process simplification here first. Changing consumer roles, shipped skill behavior or supported compatibility is a separate product decision. Historical audit: `state/audit/find-wasted-effort-2026-09-07-process-review.md` (local, not required for using this process).
