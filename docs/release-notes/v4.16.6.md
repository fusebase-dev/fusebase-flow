# v4.16.6 — upgrades proceed on Windows CRLF checkouts

**Who this affects:** projects on Windows with `core.autocrlf=true` (the Git for Windows default)
and no `.gitattributes` covering Flow's managed files. On any other setup, classification behaves
exactly as before.

This closes the limitation `v4.16.5` recorded under **Still open: upgrades on CRLF checkouts** —
for the upgrade classifier, which is what that section described. The other limits that release
named, and the broader stamper ticket behind them, stay open and are restated below so this note
is not read as more than it is.

## The blocked upgrade

**Before:** the upgrade classifier compared each managed file's bytes on disk against the digest
recorded when Flow was installed. On a CRLF checkout those bytes are not the LF bytes that digest
describes, so **every** path the new release also changed classified `changed-by-both`. `plan`
returned 9 and `bash hooks/local/upgrade.sh` stopped with exit 3. It wrote nothing and listed the
paths; there was no way to complete an unattended upgrade.

**Now:** a file whose only difference from its installed base is that git wrote it with CRLF is
recognised as that base, and the upgrade proceeds normally. Nothing for you to run, and no
configuration to change.

## How this is safe

Equivalence is granted only when **all** of the following hold for that one path:

- The file is exactly the installed base's LF bytes with every LF written as CRLF — nothing added,
  nothing removed, nothing changed.
- The comparison is anchored to the digest **recorded when Flow was installed**, not to whatever
  upstream currently holds. A committed edit that kept a copy of the baseline around is still a
  conflict.
- Git's own checkout of that content at that path produces those exact bytes. Flow asks git rather
  than guessing from configuration, and a `core.autocrlf` / `core.eol` value outside git's own
  vocabulary grants nothing instead of being interpreted.
- The path carries no `filter`, `ident` or `working-tree-encoding` attribute. Presence is what is
  checked, so a filter named `unset` or `unspecified` is refused — and never run.

Any missing evidence, any unsafe path, any conversion failure grants nothing and falls back to the
previous verdict. **A content edit cannot pass this.** Added text, removed text, changed text,
mixed line endings, a stray CR, and binary content all stay classified as your change and are
preserved.

**One case is treated as equivalent on purpose, and you should know it:** a whole-file LF↔CRLF
conversion you made **deliberately** is byte-for-byte indistinguishable from a checkout, so it **is**
treated as equivalent. If that file was also changed upstream, the upgrade takes upstream's copy
rather than stopping.

## A behaviour change worth naming

| File state | Before | Now |
|---|---|---|
| Line-ending-only difference, **and upstream changed the file** | `changed-by-both` — upgrade aborts | Upgrade proceeds with upstream's copy |
| Line-ending-only difference, **upstream did NOT change the file** | `consumer-only` — preserved and reported | `upstream-only` — refreshed with upstream's LF bytes |

The second row is the one to read twice. Flow now has proof that those bytes **are** the recorded
base, so the file is not your edit and `consumer-only` was the wrong verdict. The visible effect is
that a CRLF working copy is rewritten with LF bytes — which your own `core.autocrlf` converts back
on the next checkout.

## What this release does NOT fix

Stated plainly, because each of these can still surprise a CRLF consumer:

- **Publisher AC1 is untouched.** All three stampers still hash working-tree bytes, so a manifest
  can still describe a local copy rather than the artifact that ships. See
  `docs/backlog/stamper-hashes-worktree-not-artifact/`.
- **CRLF health checks stay exact and still report DRIFT.** Hook-layer and managed-content `verify`
  compare raw bytes. That is deliberate — byte equality is the tamper detector.
- **`--repair-managed` still reports the repair not confirmed** while other covered files remain
  CRLF; its post-repair re-verification of each bound layer is exact too.
- **The incoming source-integrity gate is unchanged.** `materialize-managed-source.sh` verifies the
  source against its own manifest before classification; a bad publisher stamp still aborts there.
- **Rewriting content and recomputing its manifest/self-hash still passes.** The self-hash is not
  authentication.
- **No automatic consumer restamp.** It would bless whatever edits are present and destroy the
  historical base.

## Residual limits of the proof itself

Recorded in `docs/backlog/stamper-hashes-worktree-not-artifact/`, not discovered later:

- **The revalidation is point-in-time, not a lock.** Local bytes and path safety are re-proved after
  git's evidence returns, which closes the window during git's run. It is not general
  concurrent-writer safety: a symlink can still be swapped between the safety check and the read,
  and bytes can change after their re-read.
- **Isolation assumes a trusted `git` on `PATH`.** The conversion runs in a scratch repository that
  reads no consumer config and no consumer attribute file, so a consumer filter driver can never be
  named there — but `git` itself is resolved through the inherited `PATH`, and a wrapper placed
  there could reintroduce exactly what the scratch repository exists to exclude.

## Maintainer tooling — no consumer behaviour change

- **T93** — a local `FF_FULL=1` / `FF_RELEASE=1` run in the maintainer tree is refused unless
  `FF_EVIDENCE_GAP` names the uncovered boundary. Hosted CI and consumer trees are exempt.
- **T94** — a local release-profile selection is refused, before any phase runs, when the committed
  manifests are stale; it relays the restamp order and never stamps on its own.
- **T95** — `docs/maintainer-execution.md` and `docs/maintainer-testing.md` carry the process wording
  the whole-session review proposed, and the stale `docs/tmp/handoff.md` became a pointer.

## Upgrade guidance

```bash
bash hooks/local/upgrade.sh
```

Consumers on 4.6.1 or earlier use `bash hooks/local/bootstrap-upgrade.sh -- --auto-yes`.

## Evidence and limits

Focused local evidence, developer feedback only. The release-profile phase `upgrade-classify-eol`
(`hooks/tests/test-upgrade-classify-eol.sh`) builds the consumer condition in separate repositories
and carries every tampering row plus six adversarial ones — an edit and a symlink swap landing
during git confirmation, a filter attribute added between the attribute snapshot and the conversion
whose driver writes a marker file, a newline inside a config value, a valueless boolean, and no
`core.*` setting in any scope. 42/42 on Windows/MSYS and in `ubuntu:24.04` (git 2.43.0) with
identical rows; 171/171 across the eleven neighbouring classifier and manifest groups. Each draft
was measured RED against the phase as it stood then. A positive control runs the same smudge driver
through git deliberately, so the marker file's absence in the negative row is not vacuous.

Cost: a digest prefilter runs before any git launch, and the git evidence is batched into 8 launches
regardless of path count. With 385 CRLF files all reaching the proof, MSYS `plan` median was 2.29 s
against 0.18 s on the base module — which returns 9 rather than 0.

Release evidence is the tagged two-platform `fusebase-flow-verify` gate on this exact SHA —
`verify-linux`, `verify-windows-msys` and `verify-gate` — which is the only publication authority.
