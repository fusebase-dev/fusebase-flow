# Fusebase Flow v4.7.1 — release notes

**Date:** 2026-08-04
**Type:** patch — one corrected instruction
**Follows:** v4.7.0 (published; **not** re-pointed — `v4.7.1` is a new tag)
**Decision:** M19 (`docs/specs/upgrade-source-integrity-and-observability/decisions.md`)
**Source:** consumer escalation `paperclip+hermes-v1`, 2026-08-04 § 3

## Summary

**One change:** `upgrade.sh`'s post-failure recovery block no longer tells you the re-run is the
same thing you just ran. It isn't, and saying so was actively misleading at the worst possible
moment.

No behaviour changed. No policy changed. No default changed. The same recovery commands are
printed; what changed is that the text is now true.

## The change

When an upgrade is interrupted or fails partway, `upgrade.sh` prints a recovery block. It used to
say:

> Recover by re-running (idempotent — the refreshed engine finishes the rest)

Step 1 of an upgrade refreshes `hooks/` — **including the engine itself**. So by the time that hint
prints, the file on disk may already have been replaced, while the failure came from the copy bash
had parsed into memory. The re-run is therefore a **different engine**, and "idempotent, it finishes
the rest" is a continuity claim across a swap that may already have happened.

It now says:

> Recover by re-running - but read this first: the content refresh may ALREADY have replaced this
> engine on disk, so the re-run executes the REFRESHED engine, not the one that just failed. Its
> behaviour may differ, INCLUDING seams it does not invoke. A clean exit from the re-run is NOT
> evidence that a check the failed engine ran still exists - if you rely on a local gate wired into
> this engine, run that gate yourself afterwards and read its verdict.

The trailing `# re-run; completes remaining steps` on the first printed command is gone as well —
it was the same continuity promise in a third wording, four lines under the paragraph that says the
behaviour may differ. The `main()` header comment carried it too, for anyone reading the source;
both are deleted rather than qualified, because any qualification would only restate the paragraph
above it.

## Why this mattered enough to correct

The reporting consumer hit the sharp version. Their own gate was wired into `upgrade.sh` and fired
from a `main()` bash had already parsed into memory — **after** the on-disk engine had been replaced
by upstream's, which has zero references to that gate. They were saved by a parse-order accident.

Had they simply re-run as instructed, a clean exit would have been **indistinguishable from "the
gate no longer exists."** The instruction was issued at the exact moment they had just been told
their security substance was gone, and it pointed at the one engine that could not tell them so
again.

**Flow deliberately does not name the consumer's gate.** The reporter suggested wording like *"the
refreshed engine does not invoke `<gate>`"*, and that is not implementable upstream: a locally wired
seam is invisible to us, so any specific name here would be fabricated. The generic statement is the
whole fix, and it is the part that matters.

## Reach, stated plainly

This corrects the text in the engine you are **running**. If your v4.7.0 engine fails an upgrade
today, you will still see the old wording — the fixed text only reaches you once you have adopted
4.7.1 and a *later* upgrade fails. That is inherent to a self-replacing engine and is not worked
around here.

## What is NOT in this release

The consumer's § 1 finding — that K7's compat-approval default is a **live open deploy gate** on an
aged tree (98 accumulated artifacts, several with no `expires_at`, one satisfying `production_deploy`
permanently) — is **real, accepted, and not fixed here.**

Work on surfacing it was attempted and **parked**: three implementation rounds failed three
adversarial reviews, and each round's fix produced the next round's defect. The root cause was a
missing contract, not missing effort — *"judge as the gate judges"* has no single answer, because
`command_policy` supplies `repo_id` + `command_digest`, `path_policy` supplies neither, and health
deferrals are not in `require_approval` at all. Shipping a reporting tool that under- or
over-states what authorizes a deploy would be worse than shipping nothing.

Scope, the design requirement, and the full history are in
`docs/backlog/compat-approval-surfacing/README.md`. Until it ships, the existing command remains the
way to see which artifacts a strict cutover will reject:

```bash
bash hooks/local/approve-local.sh --inventory
```

A second, pre-existing defect found during that work is filed separately at
`docs/backlog/self-granting-health-deferral/README.md`: a `deferred_checks` entry containing a
newline can split into two entries, letting an artifact grant itself a health-check deferral for a
canonical `check_id` it never carried. It predates this release and is not fixed here.
