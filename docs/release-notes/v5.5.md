# v5.5 — upgrade clone kept out of commits, clearer pre-commit failures, split `@fusebase/*` install advisory

> **Drop-in from v5.4.** No approval, gate or role-boundary change, and nothing new to
> configure. Upgrade as usual with `bash hooks/local/upgrade.sh`.

## Fixed: the upgrade clone can no longer be committed by accident

Flow's upgrade stages the upstream clone at `.fusebase-flow-source/`. It was not git-ignored, so
the FuseBase CLI's pre-update checkpoint (a `git add -A` before `fusebase update`) could commit it
as an embedded repository: a gitlink entry with no `.gitmodules`.

- Every `upgrade.sh`, `bootstrap-upgrade.sh` and `post-fusebase-update.sh` run now adds
  `/.fusebase-flow-source/` to `.git/info/exclude`, so `git add -A` skips the clone. Existing
  lines in that file stay as they are; one line is added.
- The template `.gitignore` lists it too, for new installs. Flow never overwrites an existing
  project's `.gitignore`; the exclude entry covers existing projects.
- If a checkpoint already committed the clone, untrack it once with
  `git rm --cached .fusebase-flow-source` and commit. The clone stays on disk and is ignored from
  then on.
- ESLint flat config reads neither ignore file. After an upgrade, delete the clone with
  `bash hooks/local/cleanup-flow-backups.sh .fusebase-flow-source`, or add it to your ESLint
  ignores with `bash hooks/local/eslint-ignore-flow-paths.sh`. See `docs/fusebase-cli-edition.md`.

## Clearer: pre-commit lint and typecheck failures

When your project's lint or typecheck command failed, the pre-commit hook printed only
`BLOCK — typecheck failed (FR-13).`, which read like a Flow failure. It now names your command
and its exit code:

```
[fusebase-flow:pre-commit] BLOCK — typecheck failed (FR-13): your project's command "npm run -s typecheck" exited 2; its output is above. Flow runs it before each commit; the failure is in the project, not in Flow.
```

Lint failures read the same way. When the checks run, and what blocks a commit, are unchanged.

## New: the health check flags split `@fusebase/*` installs

`fusebase update` rewrites only the root and SPA `package.json` files. Other install roots, such
as `apps/*/backend` or `tests/e2e`, can keep an older `@fusebase/*` SDK, and two copies of one SDK
make checks such as `instanceof ApiError` fail silently. The root cause belongs to the FuseBase
CLI; Flow now reports the symptom.

In a FuseBase CLI project (`fusebase.json` at the root), `/fusebase-health` resolves every
`@fusebase/*` dependency in every `package.json` the way Node does, skipping `node_modules/` and
dot-directories, and prints one line for each package installed at more than one version:

```
@fusebase/fusebase-gate-sdk resolves to 2 versions — 2.14.0: ., tests/e2e · 2.11.9: apps/benchmarking/backend. Separate copies break instanceof checks (e.g. ApiError) across them. Owner: FuseBase CLI version management. Fix: align these package.json entries, then npm install in each root.
```

- It is an advisory: the verdict, check counts and exit code do not change. The section headed
  "CLI version advisory" is now "CLI advisory" and carries both kinds of line.
- It is read-only: no npm, no network, no writes. It is skipped without `python3`, is bounded by
  `FFHC_CLI_PACKAGES_TIMEOUT` (default 10 s), and says so in one line if the scan does not finish.
- Fix the split as the line says. Running `fusebase update` does not fix it, because it does not
  touch those roots.

## Not shipped: a blocking pre-commit SDK version check

It would also block the FuseBase CLI's own `fusebase update` checkpoint commit; the health
advisory reports the split without blocking anything.
