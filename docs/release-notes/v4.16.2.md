# v4.16.2 — the PATH-construction ratchet now gates

**No consumer-facing behavior changes.** Nothing in the runtime, hooks, skills, recovery or upgrade
path differs from 4.16.1. This release makes an existing test-harness control selectable by the only
run that can block a publication, and corrects — forward — a claim the v4.16.1 note made about that
control.

## The change

v4.16.1 shipped `test-minimal-path-fixture.sh` §1b `callers-no-unreviewed-path-enumeration`: a source
scan over `hooks/tests/**.sh` for `for X in $PATH` loops, checked against a reviewed allowlist. The
check was real and non-vacuous. It was also in **no automatically-selected profile** — its
`minimal-path-fixture` tag sat in `FF_TAGS` alone, so it ran only under `FF_FULL=1` or an explicit
`FF_ONLY=minimal-path-fixture`. A guard nobody selects cannot go red on its own.

| Change | Detail |
|---|---|
| The tag enters the release profile | `minimal-path-fixture` is now in `FF_RELEASE_TAGS` (`hooks/tests/run-tests.sh`), so the phase runs inside `FF_RELEASE=1` on `verify-linux` **and** `verify-windows-msys` for every tagged SHA. A new `$PATH`-enumeration site is red on the run `publish` depends on. |
| The allowlist size assertion moves with it | `hooks/tests/test-ff-only.sh` `release-profile-is-explicit-32-tag-allowlist` (was 31). The profile stays an explicit allowlist: a registered phase still does not enter it silently. |
| Membership doc follows | `docs/maintainer-testing.md` records the 32-tag allowlist and the responsibility the new member carries. |
| Measured cost | ~21 s for 18 rows on MSYS, the slower of the two legs. |

The phase was audited for platform assumptions in this same change, which is what this repository's
own recurrence trigger requires of any suite entering the profile: 18/18 in `ubuntu:24.04` with
`/usr/bin/python3`, 18/18 on MSYS.

## Correction to the v4.16.1 release note — stated forward

`docs/release-notes/v4.16.1.md` says the release shipped "the ratchet that would have caught it
before a tag existed", and its table says the check is "red on MSYS and Linux alike, at the commit
that introduces a new site". **As shipped in 4.16.1, neither was true.** The check would have gone
red only if someone had chosen to run `FF_FULL=1` or named the tag explicitly; no local default, no
maintainer CI job and no release profile selected it. On the maintainer's own box, the ordinary
pre-commit and fast-local runs would not have exercised it either.

The published v4.16.1 note is **not edited** — same precedent as the v4.15.0 correction carried in
the v4.16.0/v4.16.1 notes. The corrected statement, effective from this release:

- **From v4.16.2** the ratchet is selected by the tagged two-platform gate, so a new enumeration
  site blocks publication.
- **It is still not a commit-time control.** The tag is deliberately outside `FF_FAST_TAGS` (the
  local default) and outside `fusebase-flow-maintainer.yml`'s `FF_ONLY` list. Pre-tag it fires only
  under `FF_FULL=1` or `FF_ONLY=minimal-path-fixture`.

`docs/problem-catalog/ci-linux-msys-test-divergence/problem.md` carries the same correction: its
pitfall-7 OPEN row is closed, and the entry now states exactly what the control does and does not
reach. Guardrail 8 of that entry — *a rule that lives only inside the file it protects is a comment,
not a control* — is why this release exists; a rule no profile selects is the same failure one level
up.

## Known and deliberately unchanged

- **One phase was promoted, not a batch.** Other registered phases outside the release profile were
  audited in this cycle and left alone. Notably `cli-version` (`test-cli-version-gate.sh`), which
  holds v4.16.1's sibling surviving-toolchain guard on `path_without_fusebase`, is still outside
  every automatically-selected profile; the §1b allowlist row that keeps that enumerator reviewed
  now gates, but the guard's own runtime rows do not. Promotions belong to the release that measures
  their cost.
- **No product, hook, skill, workflow or template behavior changes.** The version strings, plugin
  manifests and audit manifests move because a release moves them.

## Upgrade guidance

```bash
bash hooks/local/upgrade.sh
```

Consumers on 4.16.1 gain nothing functional and lose nothing; upgrading keeps version strings and
manifests aligned. Consumers on 4.15.3 or earlier should read `docs/release-notes/v4.16.1.md`, which
carries the 4.16.0 content.

## Evidence and limits

Focused local evidence, developer feedback only: `test-minimal-path-fixture.sh` 18/18 on MSYS and
18/18 in an `ubuntu:24.04` container with `/usr/bin/python3`; `test-ff-only.sh` full suite green with
the 32-tag assertion, and red at 31 before the profile change (so the assertion is not vacuous);
preflight 0 errors.

Release evidence is the tagged two-platform `fusebase-flow-verify` gate on this exact SHA —
`verify-linux`, `verify-windows-msys` and `verify-gate` — which is the only publication authority.
