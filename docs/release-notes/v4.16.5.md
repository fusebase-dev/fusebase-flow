# v4.16.5 — mirror recovery works on Windows checkouts that write CRLF

**Who this affects:** projects on Windows with `core.autocrlf=true` (the Git for Windows default)
and no `.gitattributes` covering Flow's files. On any other setup, recovery behaves exactly as
before. This release answers a field report against v4.15.3; one limitation from that report
remains open and is stated below under **Still open: upgrades on CRLF checkouts**.

## Mirror recovery can now repair drifted mirrors

**Before:** once git had checked out Flow's skill and agent mirrors with CRLF line endings,
`mirror-skills.sh`, `mirror-agents.sh` and `post-fusebase-update.sh` could never prove those files
were Flow's. Every drifted mirror was reported
`preserved (unowned-collision: current target bytes do not match proven committed mirror bytes)`
and stayed that way, and restoring the file with `git checkout` recreated the same state.
`mirror-skills.sh --check` also reported drift on every row of a fresh CRLF checkout.

**Now:** a mirror whose only difference from its committed version is that git wrote it with CRLF
is recognised as Flow's and repaired like any other owned mirror. The previous bytes are kept as
`<file>.pre-flow-repair`. **A line-ending-only difference needs no action from you.** `--check`
reads CRLF checkouts correctly, and the mirror manifests now record line-ending-independent
digests, so a manifest written on a Windows checkout agrees with what you commit.

**The rule, in one sentence:** recovery preserves content changes while treating the two specified
line-ending forms (every line ending LF, or every line ending CRLF) as equivalent.

| Your mirror file | What recovery does |
|---|---|
| The committed file with every LF written as CRLF, where your git configuration really writes CRLF for that path, and the path has no `filter`, `ident` or `working-tree-encoding` attribute | Repaired |
| Any added, removed or changed text, with or without CRLF | Preserved |
| Mixed line endings, or a stray CR | Preserved |
| Binary content, or a path git writes as LF (`-text`, `eol=lf`) but which holds CRLF | Preserved |
| Any path that carries a `filter` attribute, whatever the filter is called | Preserved; the filter is never run |
| An edit you have staged | Preserved |
| A file that changes while recovery is running | Preserved |
| **A whole mirror file you deliberately converted between LF and CRLF** | **Repaired.** That conversion cannot be told apart from a checkout, so it is treated as one. The `.pre-flow-repair` backup keeps your version |

Flow asks git itself whether it writes CRLF at each path, rather than guessing from configuration.

## What we did not ship from the report, and why

- **Comparing through `git hash-object`.** It runs your clean filters. A filter that drops lines
  would hide an instruction you had added from the comparison; recovery would then call the file
  Flow's and overwrite it, removing your instruction.
- **The `git show HEAD:<path> > <path>` remedy.** It discards any edits in the file, and the shell
  empties the file before git runs, so a failure leaves it truncated. With this release no remedy
  is needed.

## Still open: upgrades on CRLF checkouts

CRLF consumers may still encounter blocked upgrades: upstream-changed paths whose checkout bytes differ can abort as `changed-by-both`; see `docs/backlog/stamper-hashes-worktree-not-artifact`.

This release fixes mirror recovery only. The upgrade classifier still compares a file's bytes on
disk against the digest recorded when Flow was installed. A Flow-managed file that git re-checked
out with CRLF therefore reads as locally edited, and if the new release also changes it, an
unattended upgrade stops. It writes nothing and lists the paths. If you are certain you never
edited the listed files, an attended upgrade (without `--auto-yes`) lets you choose to take
upstream's copy for that class of files; otherwise reconcile them first.

## Ownership map cleanup

Two unused `"required": false` keys were removed from the provider-skill entries in
`hooks/local/fusebase-flow-overlays/agent-surface-ownership.json`. Nothing read them, so the
conflict check behaves exactly as before: a partially installed provider skill, and a provider
skill whose flag is enabled but which is missing, are still reported `MISSING`.

## Installing into an existing repository: the module-size ratchet (FR-25)

Both install guides said your existing large source files "would block on first touch". They do
not, and the guides now state what actually happens:

- The ratchet is live from your first commit. Flow ships a baseline of its own files, so the gate
  blocks rather than warns.
- A source file already over the ceiling (default 800 lines) may be touched or shrunk. Growing it
  is blocked whether or not you have adopted it. That block is the ratchet working as specified;
  the remedy is to move the addition into a new module.
- Adoption records those files at their current size and clears them from the `--all` audit. It
  is not permission to grow. Adopt once, from a clean tree, before feature work: the baseline is
  measured from your working files, so adopting with a grown file uncommitted records the growth
  as its limit.

See `docs/install-existing-project.md` § Activate the module-size ratchet.

## Other items from the same report

  installed the skill and the health check was right. Nothing was built.
- **F3 (CLI flags read only from project-local configuration): recorded as latent,** in

## Upgrade guidance

```bash
bash hooks/local/upgrade.sh
```

Consumers on 4.6.1 or earlier use `bash hooks/local/bootstrap-upgrade.sh -- --auto-yes`. If the
upgrade stops with `changed-by-both` on Flow files you never edited, see **Still open** above.

## Evidence and limits

Focused local evidence, developer feedback only. A separate test repository with no
`.gitattributes`, `core.autocrlf=true` and a real CRLF checkout (`hooks/tests/test-recovery-eol-equivalence.py`,
row T89 of the release-profile phase `cli-flow-recovery`) passes on Windows/MSYS and in
`ubuntu:24.04`. Its repair cases fail on v4.16.4 and its preserve cases hold on both. Filters
named `unset` and `unspecified` are included, with a smudge filter that writes a marker file; the
marker must never appear. Release evidence is the tagged two-platform `fusebase-flow-verify` gate
on this exact SHA — `verify-linux`, `verify-windows-msys` and `verify-gate` — which is the only
publication authority.
