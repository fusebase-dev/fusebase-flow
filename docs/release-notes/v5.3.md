# v5.3 — Karpathy coding guidelines for agents; comment cleanup scoped to the task

> **Drop-in from v5.2.** No hook, policy, installer, upgrade or runtime change. This release
> changes what agents working in your project are told to do while they write and review code.
> Upgrade as usual with `bash hooks/local/upgrade.sh`.

## Behavior change: agents no longer trim comments they did not need to touch

`comment-policy` (FR-22) used to say "write only two kinds of comment; remove everything else",
and agents applied the removal to **every** comment near an edit. That turned a one-line fix
into a diff full of unrelated comment deletions.

From v5.3 the rule applies only to comments **the task introduces or necessarily changes**:

- Comments an agent writes or has to modify still follow FR-22: a tripwire or a one-line
  retrieval pointer, nothing else. The "do not match surrounding comment density upward" rule
  still holds for them, even in comment-heavy files.
- Pre-existing comments next to an edit are **left as they are**. An agent may mention them;
  cleaning them up is a separate task.
- `code-review` no longer reports untouched pre-existing comments as findings.
- The comment-policy block pasted into delegated code-writing workers says the same thing, both in
  `comment-policy` and in `templates/handoff-implement.md`. Handoffs your project **already
  wrote** keep the old wording until they are regenerated.

If you relied on agents sweeping old comments as a side effect of other work, schedule that
sweep as its own task.

## New: the four Karpathy coding guidelines

`flow-skills/zoom-out/references/karpathy-guidelines.md` adds four short guidelines:
**Think Before Coding**, **Simplicity First**, **Surgical Changes** and **Goal-Driven
Execution**. The text is imported verbatim. A few clauses marked *Flow:* tie it to existing
rules: FR-25 extraction stays in scope, FR-22 governs new comments, and reproduction and retries
follow Flow's own skills.

Where agents now meet it:

| Who | When |
|---|---|
| AI Developer | Reads it before the first code edit (`role-discipline/references/ai-developer.md`) and applies it until claiming completion |
| `zoom-out` | Reads it before step 1 of the root-cause check |
| `code-review` | Judges scope and simplicity against §§2–3 (no speculative abstractions, no unrelated edits) |
| Delegated code-edit workers | Must read the AI Developer reference and must not edit beyond §3 |
| Planning, clarify, gate, Lightweight lane | Ambiguity handling cites §1; task steps are paired with a verification check and acceptance is written per §4 |

Where Flow skills already said the same thing in their own words, that wording now points to the
guideline instead of repeating it. For example, `code-review` dropped its separate "function size
and complexity" line in favor of §2. `code-review`, `comment-policy` and `zoom-out` also gained
short worked examples.
