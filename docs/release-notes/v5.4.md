# v5.4 — `/step-out` unattended runs, review depth with a durable round cap, optional model routing

> **Drop-in from v5.3.** Nothing here changes an existing approval, gate, role boundary or
> installer step. One new policy file ships, inert. Upgrade as usual with
> `bash hooks/local/upgrade.sh`.

## New: `/step-out` — keep a run going while you are away

`/step-out` is the eighth slash command. You invoke it when you are leaving mid-ticket
("I'm stepping out", "run this unattended", "I'll be away", "complete it end to end while
I'm away"). It continues every slice the run is already authorized to do, parks what it
cannot clear, and hands you back a list of exactly what it parked and why.

Type the grant in the same message as the command — scope, environment, exclusions, and an
end condition:

```
/step-out — away until 18:00 UTC. Authorized: this repo, local commits, the staging deploy.
Not authorized: production, pushes, anything touching another product.
```

That text is recorded verbatim (secrets masked) into the run-ledger at `docs/tmp/handoff.md`
§ Constraints and Guardrails, together with the run id, session, product and repo/environment.
Invoke it with no grant and it records `none supplied` and does only already-authorized local
work and safe verification.

`/step-out` is **scheduling only**. Every lifecycle rule stays with the skill that owns it:
the lane with `lightweight-lane`, the slice plan with `implementation-planning`, artifacts with
`documentation-budget`, dispatch with `task-delegation`, bounds and retries with
`liveness-discipline`, review with `code-review`, verification and deploy with
`validation-and-qa`, `smoke-testing` and `release-deploy-reporting`. The command body is 19
lines and is almost entirely pointers to those owners.

### Three limits, stated back to you before the run starts

| Limit | What it means for you |
|---|---|
| **The grant dies with the run** | It is recorded as evidence of your instruction, not as an approval artifact. A later session inherits the ledger and can read what you said; it does **not** inherit the grant and cannot act on it. |
| **It does not open a gate** | The grant satisfies "the operator asked". It does not clear an unmet Flow gate. That slice returns `BLOCKED-AT-<gate>`, and the run continues on every other independent authorized slice. `policies/approval-policy.yml` and the owning role's approval contract still gate every side effect. |
| **It never guesses a product decision** | A question the run cannot settle read-only is recorded with its options and its clearing condition, and parks **only** its dependency chain. Silence is never read as a decision. |

Blocked is not finished. Each slice reports, and the run ends with a consolidated count of
parked items and, for each one, the condition that would clear it.

### How the run reaches the command

`task-delegation`'s always-loaded description now carries the absence trigger itself, so an
absence instruction routes to `/step-out` **even when the work is one simple edit**. It also
states the exclusions: ordinary attended work, planning-only/read-only requests, and
"complete end to end" without an absence instruction are not `/step-out`.

`/step-out` is a native Claude Code slash command (`.claude/commands/step-out.md`). On Codex,
Cursor, Copilot and Gemini use the `AGENTS.md` command-equivalents table. It is the one command
with no same-named skill, so the portable route is to read the canonical body at
`hooks/local/fusebase-flow-overlays/commands/step-out.md`; Codex users who ran the opt-in
`bash hooks/local/install-codex-prompts.sh` get `/prompts:step-out`.

## `code-review`: depth follows severity, and the round cap is now durable

**Findings are graded** BLOCKER (a mandatory-stop failure) · HIGH (a serious, reachable
correctness or security risk) · MEDIUM (a bounded functional defect) · LOW (a non-blocking
improvement). Grading never downgrades a blocker the skill already names, and a known
correctness or safety blocker does not become acceptable because a review already ran once.

**Depth follows the change, not habit.**

| Change | Review |
|---|---|
| Security-relevant — code that **executes** on an auth, session, token, permission or CSRF path (docs, copy, tests or comments that merely mention those topics are not) | independent adversarial review of code and tests |
| Cross-cutting — three or more slices, or a shared module | independent adversarial review |
| HIGH risk — set per slice in the plan, confirmed at plan review | independent adversarial review |
| Ordinary change | focused review of the diff |
| Prose and doc claims | one consolidated claim-vs-evidence pass at final acceptance, not per change |

These are review-**depth** triggers only. They do not narrow the FR-21 Full-lane triggers or
`security-permissions-review`'s scope.

Rereview is scaled the same way: a BLOCKER/HIGH correction gets the affected boundary
rereviewed, MEDIUM gets a focused check of that diff, LOW rests on the implementer's evidence
unless new evidence changes the classification.

### The round cap is 2, and a fresh session inherits the count

Round 1 is the initial review; round 2 is the correction review. **Two per change is the
default maximum.** The change in v5.4 is that the count is now *recorded where it can be
checked*, because a bound that exists only in chat is unenforceable the moment the chat rolls
over or a successor picks up the work:

- The count lives in an artifact the work already owns — `docs/verification/<slug>-review.md`
  when a review record is persisted, otherwise the run-ledger `docs/tmp/handoff.md`
  § Constraints and Guardrails. **Never a new file.**
- It is one compact line with three fields: change identity (ticket/task + reviewed SHA) ·
  limit · rounds dispatched. For example: `T42 @ 3b1bfaa — review rounds: 1 of 2`.
- The agent reads it **before launching any review round** and updates it as part of that
  dispatch. No record for this change means this is round 1, and the line is written first.
- A successor agent **inherits** the count. A fresh session, a fresh reviewer or a fresh chat
  does not reset it.
- **Only your explicit authorization raises the limit** — not the actor that declared it, not
  the actor that hit it, and not an agent that merely inherited it.
- On exhaustion, unresolved findings stay blocked or deferred **with their evidence**. A
  BLOCKER is still a BLOCKER after round 2; exhaustion returns the work to you for a budget or
  scope decision, it does not make anything shippable.

Persistent LOW findings go to `docs/backlog/<slug>-low/README.md`, indexed once; an existing
matching ticket wins over a new aggregate. A persisted review record remains optional, except
that when one exists it must carry the round-accounting line.

## `task-delegation`: model routing, correction ownership, unattended scheduling

### Model routing — optional, and inert as shipped

`policies/model-routing.yml` is new. It maps five **work properties** to a model selector:

| Tier | Routed work |
|---|---|
| `planning` | decomposition, slice design, cross-slice acceptance reasoning |
| `adversarial_review` | independent defect/security analysis; prefers a different model family from the implementer when one is reachable |
| `sensitive_implementation` | code executing on auth/session/token/permission/CSRF paths, migrations, payments, infrastructure, and any slice the plan marks HIGH risk |
| `routine_implementation` | ordinary implementation, focused review, log and prose checking |
| `execution` | runs already-decided commands and reports observations; never issues an acceptance verdict |

What ships, stated exactly:

- **All five rows ship `null`.** Flow names no model and recommends none. `null` means "use the
  host's current model", so an untouched file changes nothing about how your project runs today.
- **No loader resolves these selectors.** The routing contract is instruction-level — the agent
  reads the file. There is no new runtime, no network call, and no dependency.
- **An absent, malformed, unavailable or unsupported selector is a recorded fallback, never a
  stopped run.** The run continues on the available host model, sequentially if it has to. Flow
  never stops a run over model configuration and never assumes an unverified model mapping.
  When no independent reviewer is reachable, the review still runs and is reported as a
  **same-family review**; if no independent pass is possible at all, that limitation is reported
  rather than independence being claimed.
- **A tier selects a model, never authority.** Role boundaries, approval artifacts, credential
  handling and deploy ownership are unchanged by any tier. An `execution`-tier agent gets no
  deploy or approval rights from its row.

The file carries a commented, **inactive** worked example of one operator's five-tier mapping.
It is an illustration of the syntax, not a Flow default, not a recommendation, and not a claim
that any named model exists on or is reachable from your host. The active rows stay `null`.

Put your own selection in `policies/model-routing.local.yml` (gitignored via
`policies/*.local.yml`). `upgrade.sh` refreshes `policies/` wholesale, so an edit made directly
to the committed `policies/model-routing.yml` would be overwritten on your next upgrade.

### Correction ownership

The same-agent, context-preserving reuse that the provider-limit path already required now
applies to **all** corrections: a fix to a worker's own diff goes back to that worker, which
still holds the context; a fresh agent is spawned only when the task is unrelated or that
context has demonstrably drifted. One correction owner per review round, batched by file —
never one agent per finding. Disjoint write ownership and one independently reversible outcome
per commit still bind, so batching findings never merges unrelated outcomes.

### Unattended scheduling

Active only while `/step-out` is the mode. It changes **scheduling** only; it opens no gate and
grants no authorization.

- Workers are briefed to a tighter ≤29-line return — inside, not instead of, the normal ≤80-line
  / ≤6,000-character delegated-return budget. The gate-report and deploy-report exemptions are
  unchanged: those are never truncated to fit.
- Retry exhaustion is a scheduling event. When the bounded delegate-retry envelope is spent, the
  run does not wait or sleep — it records the state, dispatches the next independent authorized
  slice, and returns to the parked one when its clearing condition is met.
- A blocked slice parks that slice **and its dependents**, with the exact question, evidence,
  options and clearing condition recorded. Every other independent authorized slice continues.

## README: "How it keeps context cost down"

The README gains a section that explains, in one place, what the framework actually does about
context cost: a small always-resident floor with everything else loaded on trigger, pointers
instead of copies, optional model routing, bounded review spend, and the two read-only audit
commands you can point at your own project (`/token-waste-audit`, `/find-wasted-effort`).

**It publishes no percentage, speedup or savings figure.** This project has not run the
controlled A/B measurement that would justify one, and an unverified number is exactly the kind
of claim Flow's own review rules reject. Every number in that section is a value you can read
out of this repository — for example the boot floor is gated by
`hooks/tests/test-boot-size.sh`, which fails the build above **42,200 bytes**, against a current
worst-case role boot of **41,215 bytes**.

## Upgrading

`bash hooks/local/upgrade.sh`. No hook behavior, installer step, approval artifact, gate or role
boundary changes in this release. `policies/model-routing.yml` is added as an inert committed
default; `hooks/local/preflight.sh` gains the `/step-out` entry in its command-surface check, so
the command's three surfaces (live file, recovery snapshot, `CLAUDE.md` reference) are verified
at the release gate rather than discovered downstream.
