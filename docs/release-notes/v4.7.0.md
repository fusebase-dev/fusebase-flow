# v4.7.0 — approval binding + upgrade conflict classification

**Theme:** the FR-12 command gate stops being replayable, and an upgrade stops overwriting your local changes.

Both halves came from one consumer report: they had wired `PreToolUse` — i.e. they were actually relying on enforcement — and a 4.5.0 → 4.6.1 upgrade silently reverted their hardening of the approval gate, which they then discovered was replayable anyway.

> ### ⚠️ Moved tag — `v4.7.0` was re-pointed
>
> An earlier `v4.7.0` tag was pushed and was consumer-visible; **at least one prerelease tester fetched it** (`docs/tmp/handoff/2026-07-30-workhub-upstream-report.md:18`) and hit the upgrade-path bugs recorded below. No GitHub Release was ever published for it. The tag has been **re-pointed** to the commit that carries those fixes; the version number is deliberately unchanged (decision M6 — `docs/specs/upgrade-source-integrity-and-observability/decisions.md`), and re-pointing required explicit operator authorization of the exact old and new commits.
>
> **If you fetched `v4.7.0` before this notice, your local tag points at the superseded commit.** Re-fetch it explicitly — an ordinary `git fetch` will not move an existing local tag:
>
> ```bash
> git fetch --force --tags origin
> git rev-parse v4.7.0     # compare against the commit named in the GitHub Release
> ```
>
> Consumers who already upgraded from the superseded tag should re-run the documented bootstrap route below; it is idempotent.

## Security — the command gate is bound, parsed, and fails closed

`hooks/shared/command_policy.py` bound an approval artifact to nothing but the `<action>` prefix of its filename. It never read the JSON body's `action`; a missing or empty `expires_at` was treated as valid forever (the expiry was **string**-compared); and an unparseable regex in a rule was silently skipped, dropping the command through to `default: allow`. One consumer measured 98 `production_deploy` artifacts on a single project, 22 with no expiry, all still authorizing deploys.

| Change | Effect |
|---|---|
| New `hooks/shared/approval_artifact.py` | One canonical judge for every carrier (`command_policy`, `path_policy`, `active-approvals.sh`, `--inventory`) — the three divergent copies of the expiry check are gone |
| Parsed UTC expiry | Missing/empty expiry is a **state**, never "valid forever"; comparison is a datetime, never lexicographic |
| Body/filename `action` agreement | An artifact whose body approves a different action no longer authorizes |
| `command_digest` + `repo_id` binding | Enforced **when present**; a bound artifact authorizes one command in one repository. Absent = action-scoped, so existing artifacts keep working |
| Fail-closed policy defects | A bad regex, a rule without a `pattern`, an unsupported `flags` entry, or a missing/empty/unparseable policy now **denies** with a policy-error reason |
| All matching rules | `fusebase deploy && npx prisma migrate deploy` requires **both** `production_deploy` and `database_migration`, reported in one message. Previously the deploy artifact alone authorized the whole line and the migration was never gated |
| Type-safe artifact loading | A JSON array, a numeric `expires_at`, `null`, or any non-object no longer raises out of `evaluate()` |

## Security — the trust model is now stated truthfully

`policies/approval-policy.yml` claimed hooks check the session's self-attested role against `approval_authors`. No code ever did, and the same file admitted as much twelve lines away. Flow does not add the check — the agent and the operator write as the same OS principal, so any author string an agent can write it can also forge, and an unenforceable check in a security control is worse than an absent one.

`approved_by` and `ticket` are now labelled **audit metadata, never authenticated authority** everywhere they are documented; `approval_authors` carries `enforced_by_hooks: false`.

## Upgrade — three-way classification replaces the whole-directory overwrite

`upgrade.sh` could tell that a managed directory *differed* from upstream, but not **who** changed it, and then `cp -R`'d upstream over it.

New `audit/managed-content-manifest.json` records a sha256 per managed path at install/upgrade — the **base**, i.e. what upstream shipped you last time. Each upgrade classifies base x local x upstream into one of ten states and applies **per file**:

| Classification | Attended | `--auto-yes` |
|---|---|---|
| `current`, `consumer-added` | no-op | no-op |
| `upstream-only`, `upstream-added`, `upstream-deleted` (clean) | apply | apply |
| `consumer-only` | preserve + report | **preserve** + report |
| `upstream-deleted` (you edited it), `consumer-deleted`, `unknown-base` | preserve + report | **preserve** + report |
| `changed-by-both` | stop + report | **abort**, nothing written |

A directory holding one file you edited now gets every *other* file refreshed. The existing directory-level `.pre-upgrade-<TS>` backup and its retention pruning are unchanged.

The conflict report collapses safe groups to counts and lists every path needing a decision **literally** — never "N files diverged", which was the consumer's specific complaint.

## Upgrade — adoption from <= 4.6.1

> **Use the 4.7.0 `bootstrap-upgrade.sh`, not the copy already installed in your repo.** Base synthesis ships *in* 4.7.0, so your stale 4.6.1 copy cannot perform it. Running the local copy is **safe but degraded**: every managed path classifies `unknown-base`, everything is preserved (K9 row 10 never aborts), your local patches survive — but you do **not** get the `changed-by-both` conflict report, and the upgrade delivers little or nothing. Measured during release smoke: `unknown-base (41)`, run completed without aborting. Fetch the release first, then run its bootstrap script.

Use the documented path:

```bash
bash hooks/local/bootstrap-upgrade.sh -- --auto-yes
```

It stages the new engine before running it (the old engine would overwrite the new one first), and **synthesizes the base** from the upstream tag matching your installed `VERSION` — byte-identical to what your last upgrade actually wrote. This is load-bearing: with no base, every path classifies `unknown-base`, everything is preserved, and the upgrade would report success while installing nothing. If the tag cannot be resolved (forked or unreleased `VERSION`), the run preserves and reports rather than guessing.

`install.sh` now records a base on fresh installs; `preflight.sh` warns when it is missing or stale; CI freshness-gates it.

## Upgrade — source integrity, backup hygiene, and observability

A prerelease consumer ran the 4.5.0 → 4.7.0 adoption hop and filed seven bugs plus one suggestion (`docs/tmp/handoff/2026-07-30-workhub-upstream-report.md`). Four needed code and are fixed here; three need none (next section). Decisions and rejected alternatives: `docs/specs/upgrade-source-integrity-and-observability/decisions.md` (M1–M10) — not restated below.

| Finding | Fix | Commit |
|---|---|---|
| **F2** — permanent, undiagnosable `FLOW_LAYER_DRIFT` on Windows | Incoming managed content is materialized from **git objects** (`git -c core.autocrlf=false -c core.eol=lf archive <commit>`) on every OS, never read from the persistent staging worktree — a worktree populated under `core.autocrlf=true` before an EOL pin keeps its pre-pin bytes forever, and `git status` stays clean the whole time. New `hooks/local/lib/materialize-managed-source.sh` is the one source boundary; a non-git source is snapshotted and verified before any write. `hook-integrity-check.sh` now names `bootstrap-upgrade.sh --repair-managed <path>`, replacing `git checkout -- <file>`, which restores the same wrong bytes | `1fc082e` |
| **F5a** — Flow's own `.pre-upgrade-<UTC>` backups failed `test-sync-allowlist.sh` | Allowlist discovery prunes exactly `<managed-stem>.pre-upgrade-<UTC>` families: an authorized stem (from `list-managed`) **and** an exact UTC stamp. No `.pre-*` wildcard; `.pre-refresh-` / `.pre-bootstrap-` are deliberately not pruned | `d5a4ced` |
| **F5b** — the recommended cleanup was `rm -rf`, which Flow's own FR-06 deny blocks | New `hooks/local/cleanup-flow-backups.sh`. Its destructive authority is exact managed-stem membership **plus** an exact `.pre-upgrade-<YYYYMMDDTHHMMSSZ>` suffix; it refuses absolute paths, `..`, globs, symlinks, non-members and anything resolving outside the repo root. The FR-06 deny is **unchanged** — the fix is a sanctioned tool, not an exception to the rail | `c88a56e` |
| **F6** — `run-tests.sh` silent for ~13 minutes: the FR-27 failure mode inside Flow's own tooling | Optional parent-owned heartbeat (`FFHC_HEARTBEAT_SECS`, default `0` = off, so every existing caller stays byte-identical). `run-tests.sh` and the health deep run opt in; the captured payload is byte-identical to a heartbeat-off run | `47a0028` |
| **S1** — no staleness signal on unconsumed approval artifacts | `created_at` written at mint time, `stale_approval_warn_after_days: 7` (a local override may only lower it), a health-check warning block that is **verdict-neutral** — it never moves the verdict, the check count or the exit code, and invalidates no approval — plus an age column in `--inventory`. An artifact without `created_at` warns as unknown-age, never rejects | `e357993` |

## Upgrade — three reported findings need no code

Recorded so the next reader is not misled: these were **not** 4.7.0 defects. F1 and F3 share one cause — the report's run was the consumer's **installed 4.5 engine**, not the 4.7.0 engine, because the upgrade was started with the local `upgrade.sh` instead of the documented bootstrap route (see the adoption section above). Verdict rationale is locked in `decisions.md` M7.

| Finding | Verdict | Evidence at this release |
|---|---|---|
| **F1** — `upgrade.sh` cannot install the new top-level `FLOW_RULES_HISTORY.md` | **already fixed** (K14, shipped in 4.7.0) | `hooks/local/upgrade.sh:263-274` drives the managed set through `managed_content_manifest.py list-managed`; the canonical list at `hooks/local/lib/managed_content_manifest.py:34-49` already contains `FLOW_RULES_HISTORY.md` (`:44`). "Drive the refresh from a manifest" — the report's own suggested fix — is what the code does |
| **F3** — `policies/` refresh silently discards consumer `exempt_globs` | **already fixed** (K9, shipped in 4.7.0) | The per-file classifier at `hooks/local/lib/managed_content_manifest.py:220-294` classes a consumer-edited managed file `consumer-only` → `auto_overwrite: False`, `report: True`. Preserve **and** report is exactly the report's requested behaviour; there is no wholesale `policies/` copy left to revert it |
| **F4** — `upgrade.sh` appends a duplicate baseline row | **refuted** | `hooks/local/lib/merge-module-size-baseline.sh:85-101` keys rows by path in an associative array (`OUT_LINES["$lp"]`, dup path → last wins) and emits one sorted row per path. The reported mechanism, append-without-dedupe, is not what the code does |

No implementation slice was written for any of the three: at this HEAD such a test would pass on arrival, which the anti-tautology contract forbids. The honest deliverable is telling consumers the upgrade route they used is unsupported — which is why the adoption warning above is now repeated in `README.md` and both install guides.

## FR-21 Lightweight-lane gate parity

Four shipped documents said a `lightweight_deploy` artifact replaces `production_deploy`, but the only `fusebase deploy` rule required `production_deploy` — so a Lightweight deploy following documented procedure was **denied by the hook**. The rule now accepts `any_of: [production_deploy, lightweight_deploy]`. The trust boundary is written down rather than implied: lane classification is **process-authoritative**; the hook cannot verify LL-eligibility.

## Behaviour changes to expect

- **Compound commands need every matched action.** `fusebase deploy && rm -r build/` now also requires `destructive_file_delete`. That is correct — the `rm` genuinely happens — and the single-message denial keeps it to one round-trip.
- **Destructive SQL is matched case-insensitively and `ALTER TABLE` is gated.** `psql -c "drop table users"` now requires `database_migration`.
- **`policies/command-policy.yml` is `schema_version: 2`** and the dead `fallthrough` key is removed (no code ever read it).
- **Strict schema mode is OFF** (`strict_approvals: false`). Expiry-less legacy artifacts are still accepted **and audit-logged**, so the acceptance is visible rather than silent. Run `bash hooks/local/approve-local.sh --inventory` to see exactly what a strict cutover will reject, and reissue before the next release flips the default. Legacy artifacts are never auto-migrated — Flow will not synthesize an approval no operator gave.

## Rollback

Code-only; no migration, no state mutation. `audit/managed-content-manifest.json` is generated and regenerates from source at any tag; legacy approval artifacts are never mutated. **Downgrading from 4.7.0 restores the replayable gate** — if you have started relying on a denial this release introduced, you lose it on downgrade.

## Known limitation — the command gate denies prose that quotes a destructive pattern (F7)

**Still present in 4.7.0.** `pre_tool_use` matches destructive patterns anywhere in the command string, including a quoted commit-message payload and a heredoc body. So a `git commit -m "…"` whose *message* describes a recursive force delete is denied although no destructive command exists. The prerelease reporter hit this while committing the very report that describes it.

**Sanctioned path today:** author the text with a file tool, then `git commit -F <file>`. That is no longer "routing around the guard" — it is the documented path for prose that quotes a destructive pattern, stated in `policies/command-policy.yml`'s header.

**Why it is not narrowed in this release** (decision M8): every narrowing proposed in the report opens a real evasion. Anchoring destructive patterns to the start of the string misses `safe && rm -rf …`; stripping the `-m` payload lets `git commit -m "$(rm -rf /)"` through, because the substitution runs before git does; ignoring heredoc bodies ignores `bash <<EOF … EOF`, which executes them; and argv-splitting *worsens* the K21 quote-fragmentation gap this release documented. The correct fix parses execution structure and needs its own adversarial corpus and review cycle — scoped in `docs/backlog/command-gate-shell-evasion/README.md`, which also carries the explicit **must-not-be-attempted** list so the next implementer does not re-derive the unsafe options.

## Deferred

Two-phase single-use approval consumption (reserve → execute → consume) is **not** in this release: both hook entry points evaluate the same command, so a claim taken at the first evaluation is burned before first use. Prerequisites are recorded in `docs/backlog/approval-single-use-consumption/README.md`. Binding removes most of the replay value meanwhile.
