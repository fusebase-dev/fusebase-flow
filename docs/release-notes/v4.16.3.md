# v4.16.3 — four more contracts gate, and the membership ratchet now gates itself

**No consumer-facing behavior changes.** Nothing in the runtime, hooks, skills, recovery or upgrade
path differs from 4.16.2. This release widens what the tagged two-platform gate selects, and closes
a recursion in the control that guards that selection.

## The recursion, first

`FF_RELEASE_TAGS` in `hooks/tests/run-tests.sh` is an explicit allowlist: a registered phase does
not enter the release profile silently. The ratchet that enforces this — the allowlist-size and
boundary-tag assertions — lives in `hooks/tests/test-ff-only.sh`.

CI ran that suite as `bash hooks/tests/test-ff-only.sh --only t33`. The `t33` slice covers the
runner's failure/timeout/zero-result contract and **excludes** the membership assertions. So on both
legs, for every tagged SHA, the ratchet guarding `FF_RELEASE_TAGS` never executed — including the
size number a promotion changes. A membership control that no run selects is the same failure class
as v4.16.2's guardrail 8, one level up.

**Fixed by widening the CI step, not by adding `ff-only` to the allowlist.** Both routes were
considered; only one works, and it was measured rather than assumed:

| Route | Verdict |
|---|---|
| `ff-only` joins `FF_RELEASE_TAGS` | **Refuted.** `FF_RELEASE=1 bash hooks/tests/test-ff-only.sh` is **17/46 FAIL**. The suite drives `run-tests.sh` with `FF_ONLY`/`FF_FULL`, and `run-tests.sh` deliberately refuses those combined with `FF_RELEASE` (rc 2). An inherited `FF_RELEASE=1` reddens both legs. |
| The CI step runs the suite unscoped | **Shipped.** `.github/workflows/fusebase-flow-verify.yml` now runs `bash hooks/tests/test-ff-only.sh` with no selector, as its own step outside `FF_RELEASE=1`. 46/46 on MSYS. |

The separate step is also the stronger shape. Profile membership would have made the ratchet's own
execution depend on the allowlist it asserts about: drop a tag and you also switch off the assertion
that would have caught you. A step that runs unconditionally cannot be disabled by the edit it
exists to catch. A tripwire at the array records why `ff-only` must stay out.

## Four phases enter the profile

`FF_RELEASE_TAGS` goes 32 -> 36. Each now runs on `verify-linux` **and** `verify-windows-msys` for
every tagged SHA, instead of only under an explicit local `FF_ONLY`.

| Tag | What it holds | MSYS | Linux | Rows |
|---|---|---|---|---|
| `cli-rendered` | Vendored assets carry no raw `<%=`. B2 shipped 40 unrendered interpolations to consumers, two on the sign-in surface. | 20 s | 1 s | 7 |
| `recovery-hint` | Recovery-hint honesty and residency assertions; sibling of the already-gated `hop-log-truth` family. | 5 s | 0 s | 6 |
| `stamp-eol-guard` | The stamper must refuse CRLF under an `eol=lf` pin. Reddened this repository's CI four times and is invisible locally by construction. | 17 s | 0 s | 18 |
| `cli-flow-recovery-selectors` | The public selector contract for `test-cli-flow-recovery.sh` — a ratchet guarding a gated suite while itself outside the profile, the same shape v4.16.2 fixed. | 56 s | 5 s | 11 |

Added cost on the slower leg: **+98 s** for the four phases, **+82 s** for the widened `ff-only`
step (18 s scoped -> 100 s unscoped). `test-ff-only.sh` asserts a 36-tag allowlist (was 32);
`docs/maintainer-testing.md` records each new member and its responsibility.

**Correction to the assessment that proposed these.** `cli-flow-recovery-selectors` was described as
spawning no engine. It does — it drives real bounded recovery groups (`t34`, `u14`, `t1`) plus
failure and timeout cases. The cost consequence is not material (56 s beside a leg already at ~20
min), so it ships; the mechanism claim was wrong and is corrected here rather than left standing.

## One phase measured and declined

`preboundary-consumed` was **not** promoted. It is green on both platforms, so this is a cost
decision and not a defect: 204 s on MSYS across 13 `bootstrap-upgrade.sh` engine hops over 9 fixture
trees, against 5-56 s for every phase that did enter. Recorded in `docs/maintainer-testing.md` as
deferred-on-cost, not as a diagnostic exclusion, so the distinction survives.

## Platform audit ran before the tag

This repository's own recurrence trigger says a newly promoted phase runs on Linux for the first
time, and that v4.16.0 went red exactly that way. Every promoted phase was therefore run in
`ubuntu:24.04` — fresh `git clone` inside the container, never a bind-mounted worktree — as well as
on MSYS. All four are green with **row counts identical on both platforms** (7/6/18/11).

The audit surfaced one latent portability defect that this release deliberately does **not** fix:
`hooks/tests/test-recovery-owned-bootstrap.py` spawns `python`, not `python3`, so
`cli-flow-recovery`'s T34 group is red in a bare container that has only `python3`. GitHub's runners
provide both (`setup-python`, plus the workflow's own `python3` shim), which is why the already-gated
parent phase has never reddened CI. It is recorded in the problem catalog as a separate outcome
rather than folded into a release.

## What this does not change

- No runtime, hook, skill, recovery or upgrade behavior. Consumers upgrading 4.16.2 -> 4.16.3 get
  the same product with a wider release gate.
- The promoted phases stay out of `FF_FAST_TAGS` and the maintainer CI `FF_ONLY` list, so the
  earliest automatic red is still the tagged gate, not the commit that breaks them.
- The explicit-allowlist property is unchanged: registration still does not imply membership.
