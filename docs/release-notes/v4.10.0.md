# v4.10.0 — FuseBase Apps CLI 0.29.8 compatibility

Full entry: `CHANGELOG.md` § [4.10.0]. This file records release evidence and the upgrade note.

Flow's vendored CLI-owned assets were last refreshed at **CLI 0.25.16**. The current CLI is
**0.29.8** — four minor versions on. Nothing Flow *executes* against the CLI was broken; what was
broken is what Flow *taught*, and in a framework whose product is the artifacts agents read, that is
a product defect rather than stale documentation.

## Why this is a minor, not a patch

New behaviour, not only fixes: the health check gained a CLI-version signal, two provider skills were
adopted (20 → 22), and the vendored CLI layer moved four minor versions.

## Upgrade note

| Change | Effect on you |
|---|---|
| Vendored CLI provider assets refreshed to 0.29.8 | The agent-facing docs under `.claude/skills/` and `.agents/skills/` now match the current CLI. If you keep local edits inside `<!-- CUSTOM:SKILL:BEGIN -->` blocks they are preserved; where 0.29.8 ships a block of the same title, upstream's corrected text wins (see below). |
| `fusebase sidecar` / `secret create` documentation corrected | Flow previously documented `--app <appId>`. CLI 0.29.8 resolves `--app` by the local `apps[].path` **only**, so the old instruction fails by reporting the app as not found. |
| Unrendered template syntax removed | 40 occurrences of raw `<%=` ETA expressions across 12 vendored files are gone. An agent reading those files was previously handed template-engine source rather than a runnable command. |
| Two provider skills adopted | `app-e2e-tests` and `invite-with-password` (20 → 22 skills, 40 → 44 mirrors). |
| `/fusebase-health` reports CLI version | A CLI **below 0.29.0** now fails the health check — Flow's vendored guidance is known-incompatible with it. Every other case (newer, older-but-supported, unreadable, absent) prints a **verdict-neutral advisory** and does not change the verdict or exit code. |

No migration, no config change.

### One superseded custom block, stated plainly

`app-dev-practices` and `file-upload/references/upload-lifecycle.md` carried `CUSTOM:SKILL` blocks that
0.29.8 now ships itself, under the same titles, as corrected supersets. Preserving Flow's older copy
would have duplicated the heading **and** kept teaching a caller identity that upstream corrected —
`client:<clientId>` is wrong; a caller id is the calling project's `productId`, and sibling apps of one
project share it. Upstream's text also adds that the extension's enforcement arrives per environment
and must not be relied on as the only authorization check today. Upstream's version is what ships.

## Platform-level finding

`docs/problem-catalog/` gains an entry for a FuseBase platform behaviour Flow previously taught
incorrectly: **a 502 during `fusebase deploy` is misread as a logout**, falsely signing users out. The
corrected pattern is a four-state session verdict (`authenticated | anon | blocked | unknown`) so a
deploy blip is never treated as anonymous, plus the proxy-returns-`302`-not-`401` case and `getMe`
status `0` (CORS, not auth).

## Also fixed — manifests described bytes that never ship

`stamp-cli-provenance.sh` and `refresh-cli-vendor.sh` wrote files via `Path.write_text()`, which
emits CRLF on Windows. `.gitattributes` normalizes those paths to LF in git, so the manifest recorded
a digest of the local copy rather than the shipped artifact. Undetectable locally by construction —
the stamper and the verifier read the same wrong bytes and agree. Both writers now pin `newline="\n"`.

## Known residuals

- The command gate still denies honest prose quoting a destructive pattern (K21/M8) — unchanged.
- Tag immutability is enforced by operator confirmation, not a repository ruleset.
- The vendored snapshot is a **materialized installation snapshot**, not a compatibility
  certification. A CLI newer than the bundled version is advisory, never a failure: your local docs
  may already be newer than Flow's if you ran a full `fusebase update`.
- `stamper-hashes-worktree-not-artifact` is open and deliberately undecided: hashing committed bytes
  would fix artifact fidelity but trade away the local-tamper detection the health check depends on.
  The trade-off is the ticket.
- Local pre-push detection of the manifest-freshness class is not shipped; CI enforces it. The phase
  built for it is preserved under `docs/backlog/local-gate-misses-manifest-freshness/` pending an
  operator decision on whether maintainer tooling belongs in the default product.
