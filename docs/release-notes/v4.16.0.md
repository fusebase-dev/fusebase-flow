# v4.16.0 — truthful hop reporting and publisher-scoped health

Two consumer-reported defects, both of the same family: a report keyed to an assumption instead of
to what actually happened. One cost a consumer a wrong bug report; the other gave a consumer a
health verdict they could not clear. Neither fix changes what recovery or upgrade *does* — only
what they tell you they did, and to whom a check applies.

## Delivered behavior

| Area | Behavior |
|---|---|
| Upgrade hop log | The summary at the end of `bash hooks/local/upgrade.sh` now reports the **observed** result for `.claude/settings.json` and for the Git fallback hooks. Settings can report: lifecycle events merged (naming the events), already current, not authorized, minimal file created with external entries unresolved, merge failed, or changed-then-a-later-surface-failed. Git hooks can report installed, custom hook preserved, or installer failure — per hook, not from one coarse match. The static line that always claimed the file "was NOT modified" and always advised `--wire-hooks` is gone. |
| Health — publisher scope | The partial-upgrade check now applies the same two predicates preflight already used: Flow ownership by `name` **and** publisher context (the release ledger `docs/release-fingerprints.md` is present). A consumer whose plugin manifests carry `name: fusebase-flow` because they were generated from Flow's no longer gets a `PARTIAL_UPGRADE` they cannot clear. |
| Health — `PUBLISHER_PACKAGING_DRIFT` | New verdict, publisher repositories only: every real drift item is a Flow-owned plugin manifest whose `version` disagrees with `VERSION`. It carries its own remediation — bump `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json` and `.claude-plugin/marketplace.json` with `VERSION` — and explicitly does **not** offer recovery, because this is packaging drift, not an interrupted upgrade. Exit code 1, alongside the other drift verdicts. A consumer tree never reaches it. |
| Health — preflight failures are their own fact | A preflight failure is now recorded when it happens, not inferred from captured text. Empty, unreadable and unparseable preflight output all reach `BROKEN`; the packaging-only interpretation is applied only when it is positively established (preflight completed, its error count reconciles with the findings it printed, and every printed finding is a packaging finding). Two preflight subchecks that previously incremented the error count silently now emit a named error line. |
| Version comparison | Plugin-manifest parity compares manifest values **as found** and escapes them only when rendering the finding, so a value that is equal to `VERSION` only after normalization is still reported as a mismatch, and ownership by `name` stays an exact identifier match. The finding is one CR/LF-free line on Linux and on Windows/MSYS alike. |

## Correction to the v4.15.0 release note — stated forward

`docs/release-notes/v4.15.0.md` never mentioned a behavior it introduced: **automatic restoration of
`.claude/settings.json` from a recorded wiring intent.** Since v4.15.0, recovery restores the Flow
lifecycle events on a tree whose earlier `--wire-hooks` wrote an ENABLED marker for the
`claude_settings` surface (`state/audit/flow-hook-wiring-intent.json`) — no new flag required.

The published v4.15.0 note is not edited; the correction is made here, forward. The current rule:

- **Marker present and ENABLED for `claude_settings`** → the events are restored automatically, and
  the run names the events it added.
- **No marker** → the file is left alone. Opt in with `--wire-hooks`; record a permanent opt-out
  with `--forget-hook-wiring`.
- **`.git/hooks`** → restored only with an ENABLED `git_hooks` marker **and** a prior installed-hook
  receipt proving Flow already owned those hooks. Marker without receipt: the run refuses and says so.

`README.md` and `docs/install-fusebase-cli-project.md` now describe this rule; both previously
asserted that recovery does not modify `.claude/settings.json` by default.

## Upgrade guidance

```bash
bash hooks/local/upgrade.sh
```

Read the run's closing summary rather than assuming the previous fixed text: it now tells you
whether settings were merged, already current, untouched for want of authorization, or left in an
uncertain state, and what happened to each Git fallback hook.

Publisher repositories that see `PUBLISHER_PACKAGING_DRIFT` from `/fusebase-health` should bump the
three plugin/marketplace manifests to match `VERSION` and re-run the check. Do not run Flow recovery
for that verdict.

## Known and deliberately unchanged

- **Event-level wiring intent was declined this cycle.** A schema-1 intent marker still authorizes
  the whole `claude_settings` surface. A per-event subset declaration was rejected because an older
  reader would treat that subset as whole-surface authorization — a silent widening on downgrade.
- **The recovery outcome channel is exclusive against consumer *bytes*, not against executable
  descendants of recovery.** Consumer content can no longer forge an outcome; code executing inside
  the recovery process tree still could. Whether consumer code executes there is not established,
  and the vector is recorded in `hooks/local/lib/recovery-outcome.sh`.
- **Timed-out or skipped preflight remains `LOCAL_UNVERIFIED`**, never OK. This release does not
  change those branches.
