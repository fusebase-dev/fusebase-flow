# v4.16.4 — the MSYS capture hang is closed at its cause, and v4.16.3's content ships

**No consumer-facing behavior changes.** `v4.16.3` was tagged, went red on `verify-windows-msys`,
and published nothing; its tag is immutable and was not moved. This release carries that content
forward and adds the fix for the defect that stopped it.

## What stopped v4.16.3

`secret-scan-staged` hit its 1800 s phase bound (rc 124) after 17 of 39 rows, on code no part of the
release had touched — 98 s on the green `v4.16.2` run of the same phase. `verify-gate` went red and
`publish` never dispatched.

The block sits between row 17 (`release-gate-self-test-tree-commits-clean`) and row 18, in the T31
setup: a throwaway repo built through `D="$(ph_repo)"` (a capture wrapping `git init` + `git add -A`
+ `git commit`) and then the REAL `hooks/git/pre-commit` captured through
`"$( ( cd "$D" && bash hooks/git/pre-commit ) 2>&1 >/dev/null )"`.

A `$(...)` substitution is a pipe the shell reads until EOF, and EOF needs EVERY write handle
closed. Under MSYS a Windows-native descendant — git, or python spawned by the hook, or anything
below them — inherits that handle, so the direct child's exit does not end the read.

## The longer leg did not cause it

`v4.16.3` took the MSYS leg from ~20 min to ~50 min, which invited the theory that four added phases
changed the runner's state. **Refuted by the logs.** Cumulative elapsed at the moment
`secret-scan-staged` started:

| Run | Phases before `secret-scan-staged` | Cumulative |
|---|---|---|
| `v4.16.2` (green, run `34444312839`) | 11 | **217 s** |
| `v4.16.3` (red, run `34506385370`) | 13 (`stamp-eol-guard` 4 s, `cli-rendered` 5 s added) | **217 s** |

Identical. The other two promoted phases (`recovery-hint`, `cli-flow-recovery-selectors`) run AFTER
it and cannot have contributed. The ~30 extra minutes on the leg ARE the hang, not extra work ahead
of it.

## What "resolved" had actually required

`docs/problem-catalog/msys-git-command-substitution-hang/` was marked **resolved** in v3.30.5. That
covered ONE converted call site, guarded by a grep for that site's exact spelling — so a capture
introduced through a wrapper function was invisible to it. Most captures on this surface are exactly
that shape: `D="$(ph_repo)"` contains no literal `git`.

Four things, not one:

| # | Change |
|---|---|
| 1 | **27 → 0 capture sites** on the gated surface — `hooks/git/pre-commit` (3), `hooks/tests/test-secret-scan-staged.sh` (23: 1 direct, 17 via repo-builder wrappers, 5 whole-hook), `hooks/tests/run-tests.sh` (1). Plus the `git ls-files \| tar` pipe in the release-gate self-test. Wrapper builders now SET a global instead of echoing a value the caller captures. |
| 2 | **A control that works by shell syntax.** `hooks/local/check-git-capture.sh` + `hooks/local/lib/git-capture-scan.py` blank comments/single quotes/quoted heredocs, walk `$(…)` and backtick substitutions with nesting, and resolve same-file function calls transitively. A grep cannot do this; that is why the previous guard missed the class. |
| 3 | **A bound at the OPERATION.** Every hook run in `secret-scan-staged` goes through `run_hook`, using the existing `ffhc_run_bounded` (tempfile capture, watchdog outside the capture, recorded owned-tree reap) with a 180 s per-run deadline. A block is named and reaped at its own call instead of surfacing as a phase wall 30 minutes later. |
| 4 | **Timeout is no longer read as a block.** `test-secret-scan-staged.sh` accepted ANY nonzero hook exit as "the secret was rejected", so a hook KILLED by a bound would have read as the control working. `hook_blocked()` is now true only when the hook ran to a verdict. |

`git-capture-guard` joins `FF_RELEASE_TAGS` (36 → 37) and runs immediately before
`secret-scan-staged` on both legs of every tagged SHA.

## The gate is proven non-vacuous

19 rows, ~25 s. Six mutations must go RED — direct capture, backtick, wrapper function, two-hop
transitive, whole-hook capture, nested — and six legitimate shapes must stay GREEN, including a git
command named inside a message string and `$(<file)`.

Two rows inject the fault itself rather than asserting about it:

| Row | Result |
|---|---|
| `retained-writer-blocks-a-command-substitution` | a script leaving ONE descendant holding its inherited handles, then exiting 3 — the enclosing `$( … )` is **still open** when a 10 s bound kills it |
| `retained-writer-does-not-block-the-tempfile-capture` | the SAME fault through the shipped capture: rc 3 in ~1 s, diagnostics intact |
| `blocked-hook-is-bounded-at-the-operation` / `…-tree-is-reaped` | a hook that never returns is killed at its 8 s deadline and its process tree is gone afterwards |

## What is NOT fixed, stated plainly

- **230 capture sites remain outside the gate** — 185 in other `hooks/tests/*.sh`, 43 in
  `hooks/local/**` operator tooling, 2 elsewhere. Gated = what runs on every commit plus the release
  harness that executes it. The rest can still burn a phase bound on a hosted MSYS runner. The
  exposure is reduced, not removed; the per-directory count in the catalog entry is the checklist,
  and adding a file to `FF_GIT_CAPTURE_GATED` is a one-line change.
- **The v4.16.3 timing did not reproduce.** 100 isolated iterations of that exact block plus a full
  phase run on an MSYS host (bash 5.3.15, git 2.55.0.windows.2) completed 39/39, worst capture
  21.9 s. Which specific descendant retained the handle on the hosted runner is UNPROVEN. What is
  proven is the mechanism (fault injection, above) and that the capture class was present at that
  exact point in the file. The fix removes the class rather than a suspected instance.
- **Historical hooks cannot be converted.** `555b897:hooks/git/pre-commit` (4 sites) and
  `41a8c6d:hooks/git/pre-commit` (5) are immutable git objects executed as RED baselines. They now
  run through the bounded `run_hook` instead.
- `docs/backlog/gate-bounds-lack-headroom/` is unchanged and still open: phase walls still have no
  measured headroom. This release bounds one phase's operations; it does not supersede that entry.
