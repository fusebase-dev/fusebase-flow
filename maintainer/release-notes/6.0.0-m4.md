# 6.0.0-m4: the 6.0.0 pass (pre-release)

The Fusebase Flow 6.0 core with its hooks finished: provider hook wiring (`install --wire-hooks`), the 6.0 `commit-msg`, the evidence-row validator inside the pre-commit, the command's hash in the heartbeat and in the audit line, and `flow health`; with the fixes from the review of 6.0.0-m3.

Needs git, bash and Python 3.10+ with PyYAML. The hooks and the two approval scripts run the first of `python3`, `python` and `py -3` that is 3.10+, so a Windows host with python.org's Python and no `python3` works too; PyYAML must be installed for that one. Get this release; the second line installs PyYAML:

```
git clone --depth 1 --branch 6.0.0-m4 https://github.com/fusebase-dev/fusebase-flow.git fusebase-flow-6.0.0-m4
pip install -r fusebase-flow-6.0.0-m4/hooks/requirements.txt
```

**Project on 6.0.0-m2 or 6.0.0-m3.** Re-run the install. It adds the new files, replaces the Flow files you have not edited, keeps the ones you edited, rewrites its marked blocks in `.gitattributes` and `.gitignore` and `audit/flow-install.json`, reinstalls the three git hooks, and touches nothing else:

```
python fusebase-flow-6.0.0-m4/maintainer/flow.py install --target <your-project> --providers claude,codex
```

If you edited `policies/approval-policy.yml`, the re-run keeps your copy, which has no `gate_rounds`; the gate then allows 2 rounds, the shipped value. Add `--register-reader` to schedule the heartbeat reader every 5 minutes (`schtasks` on Windows, crontab elsewhere): it writes your crontab only after `crontab -l` exits 0 or says there is no crontab yet, adds no second line for the same project, and refuses a `schtasks` command over 261 characters; when it refuses or fails it prints the line to add by hand, and the install still exits 0. Add `--wire-hooks` to merge Flow's two tool handlers into `.claude/settings.json` and `.codex/hooks.json` beside the CLI's entries, which it never changes; a plain install writes neither file. Commit the result as the protected commit `workflows/lifecycle.md` describes: stage it by name, mint with `FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh` (the default 15 minutes can run out during a slow pre-commit), commit with a `flow:` subject, such as `flow: upgrade Fusebase Flow 6.0.0-m3 to 6.0.0-m4`, then run the same script with `--consume`. A `flow:` commit needs no task, so it also goes through in a project that already has a plan; it passes only when every staged path is a Flow file with the bytes `audit/flow-install.json` records, one of the four documents, or a change inside Flow's marked block in `AGENTS.md`, `CLAUDE.md`, `.gitattributes` or `.gitignore`. Then check it, read-only: `python fusebase-flow-6.0.0-m4/maintainer/flow.py health --target <your-project>` exits 0 when the install is healthy.

**Commit subjects change.** The new `commit-msg` takes exactly one `T<n>` in the subject, a task of `docs/flow/phases.md` at HEAD once that file has tasks; `plan:` and `ship:` only on the files the plan and ship skills name; `flow:` only on Flow's own files, for Flow's install, migration and upgrade commits; a merge by git's state. The `docs:`, `chore:` and other prefix exemptions are gone, except for the FuseBase CLI's two update checkpoints, `chore(update): pre app update (<date>)` and `chore(update): post app update (<date>)`, so `fusebase update` can commit them: `exempt_subjects` in `policies/evidence-classes.yml` names them, and only the committed file counts. If you edited that file, the re-run keeps your copy without the key; copy the key from the release's file. A commit outside the trivial tier (`policies/evidence-classes.yml`, empty by default) needs its task's backlog item.

**New project:** the same install command, at the top level of a git repository.

**Project on Flow 5.x.** First run the dry run. It prints what it would remove, replace and add, and what it never touches, and changes nothing. The dry run runs the structural preflight; `--apply` runs the project's lint and typecheck before any change; so a dry run that exits 0 means the migration will go through only once those two also pass by hand. Then run the migration:

```
python fusebase-flow-6.0.0-m4/maintainer/flow.py migrate --target <your-project> --providers claude,codex
python fusebase-flow-6.0.0-m4/maintainer/flow.py migrate --target <your-project> --providers claude,codex --apply --go-ahead
```

`--apply` first checks everything that could stop it, and changes nothing if a check fails. It copies every file it removes or replaces into `.flow-migrate-<UTC time>/`. The migration lands as one commit, `flow: migrate Fusebase Flow <5.x version> to 6.0.0-m4`, through the new git hooks, and writes the Flow `.gitignore` block.

**Undo.** The end of `--apply` and the migration report in `docs/flow/ledger.md` print this block with the values filled in. Paste it into Git Bash at the project's top level, as one unit. It checks out the pre-migration commit on a new branch, puts the 5.x git hooks back and restores the untracked files the migration removed or overwrote, from the backup folder. If that folder is gone, the block takes the hooks from the 5.x tree's `hooks/git/` and says so, and those untracked files cannot be restored; if that tree has no `hooks/git/` copies either, it stops before anything changes. It stops at the first step that fails, and your shell stays open. The branch you migrated keeps the migration commit.

```
( set -e
  if [ -d ".flow-migrate-<UTC time>" ]; then :; elif git cat-file -e "<the pre-migration commit>:hooks/git/pre-commit" 2>/dev/null && git cat-file -e "<the pre-migration commit>:hooks/git/commit-msg" 2>/dev/null && git cat-file -e "<the pre-migration commit>:hooks/git/pre-push" 2>/dev/null; then echo "NOTE: the backup folder .flow-migrate-<UTC time>/ is gone: the git hooks come from the 5.x tree's hooks/git/, and the untracked files the migration removed or overwrote cannot be restored"; else echo "STOPPED before any change: the backup folder .flow-migrate-<UTC time>/ is gone, and the pre-migration commit does not hold all three of hooks/git/pre-commit, commit-msg and pre-push to put the 5.x git hooks back from"; false; fi
  git checkout -b flow-5x-<UTC time> <the pre-migration commit>
  for h in pre-commit commit-msg pre-push; do if [ -f ".flow-migrate-<UTC time>/.git-hooks/$h" ]; then cp -p -- ".flow-migrate-<UTC time>/.git-hooks/$h" "$(git rev-parse --git-common-dir)/hooks/$h"; elif [ -d ".flow-migrate-<UTC time>" ]; then rm -f -- "$(git rev-parse --git-common-dir)/hooks/$h"; else git cat-file blob "<the pre-migration commit>:hooks/git/$h" > "$(git rev-parse --git-common-dir)/hooks/$h"; chmod +x -- "$(git rev-parse --git-common-dir)/hooks/$h"; fi; done
  if [ -d ".flow-migrate-<UTC time>" ]; then while IFS= read -r p; do mkdir -p -- "$(dirname -- "$p")"; cp -p -- ".flow-migrate-<UTC time>/$p" "$p"; done < ".flow-migrate-<UTC time>/.migrate/untracked.txt"; fi
)
```

## What is new

| Piece | What it does |
|---|---|
| `install --wire-hooks` (`maintainer/wire.py`) | Claude Code: `PreToolUse`, `PostToolUse` and `PostToolUseFailure` on Bash, PowerShell, Edit, Write, MultiEdit and NotebookEdit in `.claude/settings.json`. Codex: `PreToolUse` and `PostToolUse` on Bash in `.codex/hooks.json`. Merged beside the CLI's entries; a file a JSON round trip would reformat is refused, left as it is, and the entries are printed to add by hand; a second run writes nothing |
| `hooks/handlers/pre_tool_use.py`, `post_tool_use.py`, `hooks/local/run-handler.sh` | The two tool handlers and their interpreter wrapper, installed by every install and wired only by `--wire-hooks`. `post_tool_use.py` writes the audit line for a command: its ids and the sha256 of the command, never its text, and no git call. `pre_tool_use.py`'s line for a command carries the tool name, the sha256 and a fixed reason (`FR-12: approval required (<actions>)` on an approval rule), never the command; the agent still sees the full message. The reader counts the hash of completed calls only |
| `hooks/git/commit-msg`, `hooks/local/lib/commit_msg.py`, `flow_owned.py` | The subject rules above (handoff WP 10, decision 10(c)). It finds Python as the pre-commit does, `python3`, then `python`, then `py -3`; without PyYAML it blocks with one line that names the `pip install` to run |
| Pre-commit evidence stage | A commit that stages `docs/flow/evidence.md`, `docs/flow/evidence/<phase>.md` or a file under `state/runs/` runs `validate_evidence.py --staged`: a PASS row that does not hold blocks; a row not written yet, or recorded as FAIL, does not. Other commits print nothing more |
| `bounded-run` heartbeat line 2 | `cmd sha256=<hex>`, the sha256 of the command's arguments; the reader and the checks count it instead of the label |
| `flow.py health --target <dir>` (`maintainer/health.py`) | Read-only: the version, the files changed or missing since the install, the marked blocks, the git hooks, the wiring per provider, the reader's schedule and `state/status.line`. Exit 0 healthy, 1 not, 2 no install |
| Flag ids (`checks.py`) | A flag's id is its kind, task and path or variable, so a ruling survives a re-run that moved a line number, a count or the minutes; a row that no longer fires stays, marked `[stale]`; added columns stay; a ruling under the 6.0.0-m3 id still finds its flag |
| The Flow `.gitignore` block | Adds `state/returns/` and `state/audit.log.jsonl`. `state/flags/`, `state/gate/`, `state/done/`, `state/deploys/` and `state/runs/` are records, committed |
| `PYTHONSAFEPATH=1` | `gate.py`, `checks.py` and `flow.py migrate` import their siblings with it set |

## Kernel changes and the 5.x line

Each kernel change landed on 5.x first and was copied here with `maintainer/kernel.lock` updated in the same commit (37 files). The 5.x commits sit on a local branch from 5.x `main` at `731acb69`, each with 5.x's two manifests restamped: `834901cd` (`bounded-run` line 2), `2caaf8d1` (the pre-commit evidence stage, which does nothing on a 5.x tree: it runs only where `hooks/local/validate_evidence.py` exists), `0b69e6c7` (`post_tool_use.py`'s audit line, which 5.x's own wiring never reaches), `c7ddf591` (`pre_tool_use.py`'s audit line: the command's hash and a fixed reason, never its text) and `a85b59ec` (`write-bootstrap-approval.sh` and `approve-local.sh` find `python3`, `python` or `py -3`). **They are not yet public:** no GitHub branch carries them, and pushing them to 5.x needs the owner's approval. The new `commit-msg` is core only, by the owner's answer of 2026-10-19: it concerns the four documents and the trivial-tier policy, which 5.x trees do not have (decision 10(c)'s designed divergence); 5.x keeps its own.

## Limits

- Codex: unproven. `--wire-hooks` writes `.codex/hooks.json`, and Codex asks you to trust each project hook before it runs one; no slice has run on Codex yet. Codex reports edits as `apply_patch`, which the handlers do not parse, so the tool-time path and secret checks are unenforced there; the git pre-commit covers both. `docs/provider-coverage.md` lists each element.
- `state/status.line` says a provider is `wired` when its settings name a Flow handler that exists; that proves no Codex run.
- `pre_tool_use.py`'s audit lines carry the tool name and the command's hash, not yet the call ids.
- The tool-call counts come from the builder's return file; the audit line is not read for them yet.
- `hooks/local/check-module-size.sh --write-baseline` still prints `chore(fr25): adopt module-size baseline`, which the new `commit-msg` rejects, and the changed baseline is not a `flow:` commit either: commit it under a task's `T<n>`. That script is kernel text and changes on 5.x first.

This is a pre-release. CI gates it on Linux; the Windows (Git Bash) run reports but gates nothing until 6.0.0.
