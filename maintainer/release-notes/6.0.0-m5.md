# 6.0.0-m5: the fixes from the 6.0.0-m4 review (pre-release)

The Fusebase Flow 6.0 core with the fixes the review of 6.0.0-m4 asked for: branches and worktrees older than the migration are told which branch to merge, and the FuseBase CLI's two update checkpoints commit there; those two checkpoints skip lint and typecheck with a warning; no URL userinfo reaches the audit log; and three text and record fixes.

Needs git, bash and Python 3.10+ with PyYAML. The hooks and the two approval scripts run the first of `python3`, `python` and `py -3` that is 3.10+, so a Windows host with python.org's Python and no `python3` works too. PyYAML must be installed for that one, with its own pip: `<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m5/hooks/requirements.txt`, not a bare `pip`, which can belong to another Python. Get this release; the second line installs PyYAML:

```
git clone --depth 1 --branch 6.0.0-m5 https://github.com/fusebase-dev/fusebase-flow.git fusebase-flow-6.0.0-m5
<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m5/hooks/requirements.txt
```

That is usually `python3` on Linux and macOS; on Windows with python.org's Python it is `python` (`python -m pip install -r fusebase-flow-6.0.0-m5/hooks/requirements.txt`) or `py -3`. Windows' default App execution aliases make `python3` the Microsoft Store shortcut, which fails the 3.10+ check, so Flow goes on to `python` and `py -3`; when none of the three is Python 3.10+, the commit is refused until you turn off the python.exe and python3.exe App execution aliases (Settings, Apps, Advanced app settings) or install Python 3.10+.

**Project on 6.0.0-m4, or an earlier 6.0.0 pre-release.** Run the install from the project's main worktree (in a linked worktree, made by `git worktree add`, it refuses and names the main one). It adds the new files, replaces the Flow files you have not edited, keeps the ones you edited, rewrites its marked blocks in `.gitattributes` and `.gitignore` and `audit/flow-install.json`, reinstalls the three git hooks, and touches nothing else:

```
python fusebase-flow-6.0.0-m5/maintainer/flow.py install --target <your-project> --providers claude,codex
```

If you edited `policies/approval-policy.yml`, the re-run keeps your copy, which has no `gate_rounds`; the gate then allows 2 rounds, the shipped value. Add `--register-reader` to schedule the heartbeat reader every 5 minutes (`schtasks` on Windows, crontab elsewhere): it writes your crontab only after `crontab -l` exits 0 or says there is no crontab yet, adds no second line for the same project, and refuses a `schtasks` command over 261 characters; when it refuses or fails it prints the line to add by hand, and the install still exits 0. `--wire-hooks` merges Flow's two tool handlers into `.claude/settings.json` and `.codex/hooks.json` beside the CLI's entries, which it never changes; a plain install writes neither file. An upgrade needs no `--wire-hooks`: the wiring you have stays as it is (see "Upgrading a 6.0.0-m4 project, step by step"). Commit the result as the protected commit `workflows/lifecycle.md` describes: stage it by name, mint with `FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh` (the default 15 minutes can run out during a slow pre-commit), commit with a `flow:` subject, such as `flow: upgrade Fusebase Flow 6.0.0-m4 to 6.0.0-m5`, then run the same script with `--consume`. A `flow:` commit needs no task, so it also goes through in a project that already has a plan; it passes only when every staged path is a Flow file with the bytes `audit/flow-install.json` records, one of the four documents, or a change inside Flow's marked block in `AGENTS.md`, `CLAUDE.md`, `.gitattributes` or `.gitignore`. Then check it, read-only: `python fusebase-flow-6.0.0-m5/maintainer/flow.py health --target <your-project>` exits 0 when the install is healthy.

**Open branches and worktrees.** Git keeps one set of hooks for a whole repository, so the 6.0 hooks run on every branch and in every worktree as soon as one branch installs or migrates. `install` and `migrate` list the other local branches and linked worktrees that do not carry Flow 6.0 yet. On such a branch an ordinary commit is refused with a message that names the migrated branch: merge it in first (`git merge <the migrated branch>`), then commit. The FuseBase CLI's two update checkpoints still commit there, without lint and typecheck. Do this for each branch and worktree in the list before its next commit; a release or hotfix branch gets the whole migration with that merge. `git log --all --oneline --grep='^flow: migrate'` finds the migration commit, and `git branch -a --contains <that commit>` the branches that hold it.

**Start a fresh agent session.** After migrating or upgrading, close the agent sessions that were open and start new ones: a session keeps the rules it loaded when it started, so an open one goes on following 5.x's (or the previous release's).

**Commit subjects.** `commit-msg` takes exactly one `T<n>` in the subject, a task of `docs/flow/phases.md` at HEAD once that file has tasks; `plan:` and `ship:` only on the files the plan and ship skills name; `flow:` only on Flow's own files, for Flow's install, migration and upgrade commits; a merge by git's state. The FuseBase CLI's two update checkpoints, `chore(update): pre app update (<date>)` and `chore(update): post app update (<date>)`, pass whatever they stage, so `fusebase update` can commit them: `exempt_subjects` in `policies/evidence-classes.yml` names them, and only the committed file counts. If you edited that file, the re-run keeps your copy without the key; copy the key from the release's file. A commit outside the trivial tier (`policies/evidence-classes.yml`, empty by default) needs its task's backlog item.

**Lint and typecheck.** Git runs the pre-commit before the commit message exists, so Flow 6.0 runs your project's lint and typecheck in `commit-msg`, after the subject check, whenever the `commit-msg` git runs is Flow's (with a hook manager such as Husky in `core.hooksPath`, they stay in the pre-commit): a commit with a task still runs them and is refused when they fail. The two CLI checkpoints skip them and print a warning saying they were not run; run them yourself after `fusebase update`. A merge runs neither, as before.

**New project:** the same install command, at the top level of a git repository's main worktree.

**Project on Flow 5.x.** First run the dry run. It prints what it would remove, replace and add, what it never touches, and the open branches and worktrees above, and changes nothing. The dry run runs the structural preflight; `--apply` runs the project's lint and typecheck before any change; so a dry run that exits 0 means the migration will go through only once those two also pass by hand. Then run the migration, from the main worktree:

```
python fusebase-flow-6.0.0-m5/maintainer/flow.py migrate --target <your-project> --providers claude,codex
python fusebase-flow-6.0.0-m5/maintainer/flow.py migrate --target <your-project> --providers claude,codex --apply --go-ahead
```

`--apply` first checks everything that could stop it, and changes nothing if a check fails. It copies every file it removes or replaces into `.flow-migrate-<UTC time>/`. The migration lands as one commit, `flow: migrate Fusebase Flow <5.x version> to 6.0.0-m5`, through the new git hooks, and writes the Flow `.gitignore` block. Its report, at the top of `docs/flow/ledger.md`, ends with the health check to run after that commit.

**Undo.** The end of `--apply` and the migration report in `docs/flow/ledger.md` print this block with the values filled in. Paste it into Git Bash at the project's top level, as one unit. It checks out the pre-migration commit on a new branch, puts the 5.x git hooks back and restores the untracked files the migration removed or overwrote, from the backup folder. If that folder is gone, the block takes the hooks from the 5.x tree's `hooks/git/` and says so, and those untracked files cannot be restored; if that tree has no `hooks/git/` copies either, it stops before anything changes. It stops at the first step that fails, and your shell stays open. The branch you migrated keeps the migration commit.

```
( set -e
  if [ -d ".flow-migrate-<UTC time>" ]; then :; elif git cat-file -e "<the pre-migration commit>:hooks/git/pre-commit" 2>/dev/null && git cat-file -e "<the pre-migration commit>:hooks/git/commit-msg" 2>/dev/null && git cat-file -e "<the pre-migration commit>:hooks/git/pre-push" 2>/dev/null; then echo "NOTE: the backup folder .flow-migrate-<UTC time>/ is gone: the git hooks come from the 5.x tree's hooks/git/, and the untracked files the migration removed or overwrote cannot be restored"; else echo "STOPPED before any change: the backup folder .flow-migrate-<UTC time>/ is gone, and the pre-migration commit does not hold all three of hooks/git/pre-commit, commit-msg and pre-push to put the 5.x git hooks back from"; false; fi
  git checkout -b flow-5x-<UTC time> <the pre-migration commit>
  for h in pre-commit commit-msg pre-push; do if [ -f ".flow-migrate-<UTC time>/.git-hooks/$h" ]; then cp -p -- ".flow-migrate-<UTC time>/.git-hooks/$h" "$(git rev-parse --git-common-dir)/hooks/$h"; elif [ -d ".flow-migrate-<UTC time>" ]; then rm -f -- "$(git rev-parse --git-common-dir)/hooks/$h"; else git cat-file blob "<the pre-migration commit>:hooks/git/$h" > "$(git rev-parse --git-common-dir)/hooks/$h"; chmod +x -- "$(git rev-parse --git-common-dir)/hooks/$h"; fi; done
  if [ -d ".flow-migrate-<UTC time>" ]; then while IFS= read -r p; do mkdir -p -- "$(dirname -- "$p")"; cp -p -- ".flow-migrate-<UTC time>/$p" "$p"; done < ".flow-migrate-<UTC time>/.migrate/untracked.txt"; fi
)
```

## Upgrading a 6.0.0-m4 project, step by step

Run these in Git Bash (any terminal elsewhere), in the folder that holds your project's folder; `<your-project>` is that folder's name. Start from a clean tree: commit or stash your own work first, and close the agent sessions open on the project (a session keeps the rules it loaded). The same lines serve every 6.0.0-m4 install: one with no tool hooks wired, one with Claude Code alone wired, and one with Claude Code and Codex wired. On the install line, give the providers your install already has: `audit/flow-install.json` lists them under `providers` (both live projects have `claude,codex`). Leave `--wire-hooks` off: the wiring in `.claude/settings.json` and `.codex/hooks.json` stays as it is, since Flow's entries did not change from 6.0.0-m4, and `--wire-hooks` with `claude,codex` would add a `.codex/hooks.json` a Claude-only wiring never had.

```
git clone --depth 1 --branch 6.0.0-m5 https://github.com/fusebase-dev/fusebase-flow.git fusebase-flow-6.0.0-m5
<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m5/hooks/requirements.txt
python fusebase-flow-6.0.0-m5/maintainer/flow.py install --target <your-project> --providers <the providers audit/flow-install.json lists>
cd <your-project>
git status --short
git add -u
FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh
git commit -m "flow: upgrade Fusebase Flow 6.0.0-m4 to 6.0.0-m5"
bash hooks/local/write-bootstrap-approval.sh --consume
cd ..
python fusebase-flow-6.0.0-m5/maintainer/flow.py health --target <your-project>
```

What each step shows, as on the copies these steps were tested on:
- the install lists `added: 0` and the Flow files it replaced. Its line `provider hook wiring: not written` means it wrote no wiring this time; the wiring you have stays. When other local branches or worktrees have no Flow 6.0 files, a WARNING names each one that must merge this branch before its next commit;
- `git status --short` lists only ` M` lines, the Flow files the install changed. If it lists anything else, stop: that is your work; commit or stash it, then go on. `git add -u` stages exactly those changed files;
- the commit runs the secret scan, the protected paths and the module size, then your lint and typecheck in `commit-msg`; it takes a few minutes on a large project, which the 30-minute mint covers;
- health ends `HEALTH: healthy` and exits 0; for an install with Claude Code alone wired it shows `wiring: claude wired` and `wiring: codex unenforced`, as before the upgrade.

In a wired Claude Code session, the steps inside the project (`git status --short`, `git add -u`, the mint, the commit, `--consume` and `cd ..`) go through the project's own `hooks/handlers/pre_tool_use.py`, which allows each of them; the agent mints only on the operator's go-ahead in chat. Outside the project folder that handler stops with an error (it cannot find the project's git root) without blocking the command, so run the clone, the install and health in a terminal.

## What is new

| Piece | What it does |
|---|---|
| `hooks/git/commit-msg` on a branch older than the migration | Where the work tree has no `hooks/local/lib/commit_msg.py`, an ordinary commit is refused with the branch that holds the `flow: migrate` commit and `git merge <it>`, or, when there is none, how to find it; the CLI's two checkpoints pass. Where HEAD has the file and only the work tree lost it, the message says to restore it from HEAD (`git checkout HEAD -- <the file>`) |
| `flow.py install` and `flow.py migrate` | Refuse in a linked worktree, naming the main one, and change nothing. List the other local branches and linked worktrees without Flow 6.0's files, in the install report and in the migration's dry run and apply |
| Lint and typecheck in `commit-msg` | The pre-commit leaves them to the `commit-msg` git will run (in `core.hooksPath` when that is set, else in the repository's hooks folder) only when that file is executable and carries the line `# fusebase-flow-commit-msg: runs lint and typecheck` (Flow 6.0's), and no merge is in progress; otherwise it runs them itself, as in 6.0.0-m4; `commit-msg` runs them after the subject check, skips them with a warning for the two CLI checkpoints, and runs none on a merge. A conflicted merge's pre-commit still runs them. 5.x's `commit-msg` has no such line |
| `hooks/shared/audit_logger.py` | Every string an audit line carries, the reason and every extra field, keeps `scheme://host/path` of a URL and loses its `user[:password]@`; the pre-push's line for a blocked push names the URL without its token |
| The migration report | Names the health check to run after the migration commit: `flow.py health --target .` from the project's top level |
| `policies/module-size-baseline.txt` | The core's copy has no row: its `hooks/local/upgrade.sh` row named a 5.x file 6.0 does not ship. An upgraded project keeps its `821 hooks/local/upgrade.sh` row: install carries it as one of the project's own rows |
| `validate_evidence.py`, `gate.py`: a blocked row with an owner answer | An evidence row whose status is `BLOCKED-AT-<reason>` and that cites, in its Status or Note, an owner answer `A<n>` that `docs/flow/backlog.md` has under `## Answers` does not fail the gate. It is listed as blocked, never as PASS: on its own line, in the `EVIDENCE: BLOCKED` summary, and in the gate's verdict line. Without such an answer it fails as before |
| The approval mint for a delete | `bash hooks/local/approve-local.sh destructive_file_delete <slug> '<reason>' --command '<the rm>'`, as one whole command with the action written exactly so, is judged without the text of its `--command` argument, so it is no longer refused by the delete rule it mints for. Every other action's mint is judged whole, as in 6.0.0-m4. Anything chained or substituted outside that argument is judged as before, and so is the approved command when it runs |
| `install --wire-hooks`, the entries to add by hand | When it leaves `.claude/settings.json` or `.codex/hooks.json` as it is, the entries it prints to add by hand are what its own merge writes: per event, a list of matcher groups (`[{"matcher": ..., "hooks": [{"type": "command", "command": ..., "timeout": ...}]}]`), which Claude Code's schema takes; 6.0.0-m4 printed one object per event, for both files |
| `install --register-reader` on Windows | The task runs `pythonw.exe`: beside this Python, else beside the `py` launcher's Python 3, else `pythonw` on PATH. Only when none is found does it run `python.exe`, and install then warns that a console window will open every 5 minutes and how to avoid it |

From 6.0.0-m4: `834901cd`, `2caaf8d1`, `0b69e6c7`, `c7ddf591`, `a85b59ec`, `13c58ca1` and `a395d17d`; `2caaf8d1` reached 5.x `main` as `4f6c12bc` on 2026-10-19. ## Limits

- Codex: unproven. `--wire-hooks` writes `.codex/hooks.json`, and Codex asks you to trust each project hook before it runs one; no slice has run on Codex yet. Codex reports edits as `apply_patch`, which the handlers do not parse, so the tool-time path and secret checks are unenforced there; the git pre-commit covers both. `docs/provider-coverage.md` lists each element.
- `state/status.line` says a provider is `wired` when its settings name a Flow handler that exists; that proves no Codex run.
- `pre_tool_use.py`'s audit lines carry the tool name and the command's hash, not yet the call ids.
- The tool-call counts come from the builder's return file; the audit line is not read for them yet.
- `hooks/local/check-module-size.sh --write-baseline` still prints `chore(fr25): adopt module-size baseline`, which the new `commit-msg` rejects, and the changed baseline is not a `flow:` commit either: commit it under a task's `T<n>`. That script is kernel text and changes on 5.x first.
- Lint and typecheck print their lines with the `[fusebase-flow:pre-commit]` prefix even when `commit-msg` runs them: that text is kernel, shared with 5.x.
- What the terminal shows for a blocked push is unchanged: the pre-push still prints the push URL as git gave it; only the audit log drops its userinfo.
- `hooks/local/install-git-hooks.sh` run by hand in a linked worktree still writes the shared hooks; `flow.py install` refuses there.
- A delete mint run any other way (an absolute path to the script, an environment prefix, `bash -c`, the action quoted) gets no exemption and is refused as before; so is every other action's mint whose `--command` text a rule gates, such as a deploy or a push to main: an agent asks the operator to run that one in a terminal.
- The two CLI checkpoints commit with lint and typecheck red; `FLOW_RULES.md` rule 6 does not name that exception yet.

This is a pre-release. CI gates it on Linux; the Windows (Git Bash) run reports but gates nothing until 6.0.0.
