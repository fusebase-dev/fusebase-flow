# 6.0.0-m6: one go-ahead for a policy edit under wired hooks, and the owner's m6 list (pre-release)

The Fusebase Flow 6.0 core with: one operator go-ahead in chat that lets an agent edit and commit a Flow policy file while Claude Code's tool hooks are wired; the twelve items of the owner's m6 list (the flaky check scoped by phase, the gate's dispatch line, review rounds counted, each commit stage's time kept and the planner's tool calls counted, one commit at a time, a criterion that depends on its own phase's gate refused, health asking the scheduler, `state/` records without lint, the project's own module-size baseline, the orphan 5.x backups removed, and the guidance after a migration); a test fix for the race that stopped the 6.0.0-m5 publish; and the fixes of its review with the owner's four additions: no console window from the reader or any hook script on Windows, a FLAKY row resolved only by a counted reproduction or an owner answer, a staged FAIL row never shown as PASS, and a pre-deploy baseline run allowed before its deploy. Both live projects upgrade from 6.0.0-m4 in one step (see "Upgrading a 6.0.0-m4 project to 6.0.0-m6 in one step").

6.0.0-m5's release page was published on its fourth CI attempt; the three failures were a test race (a copy of a test repository against git's background packing) that 6.0.0-m6 fixes (T288). Its tag stays where it was.

Needs git, bash and Python 3.10+ with PyYAML. The hooks and the two approval scripts run the first of `python3`, `python` and `py -3` that is 3.10+, so a Windows host with python.org's Python and no `python3` works too. PyYAML must be installed for that one, with its own pip: `<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m6/hooks/requirements.txt`, not a bare `pip`, which can belong to another Python. Get this release; the second line installs PyYAML:

```
git clone --depth 1 --branch 6.0.0-m6 https://github.com/fusebase-dev/fusebase-flow.git fusebase-flow-6.0.0-m6
<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m6/hooks/requirements.txt
```

That is usually `python3` on Linux and macOS; on Windows with python.org's Python it is `python` (`python -m pip install -r fusebase-flow-6.0.0-m6/hooks/requirements.txt`) or `py -3`. Windows' default App execution aliases make `python3` the Microsoft Store shortcut, which fails the 3.10+ check, so Flow goes on to `python` and `py -3`; when none of the three is Python 3.10+, the commit is refused until you turn off the python.exe and python3.exe App execution aliases (Settings, Apps, Advanced app settings) or install Python 3.10+.

**Project on 6.0.0-m4 or 6.0.0-m5, or an earlier 6.0.0 pre-release.** Run the install from the project's main worktree (in a linked worktree, made by `git worktree add`, it refuses and names the main one). It adds the new files, replaces the Flow files you have not edited, keeps the ones you edited, rewrites its marked blocks in `.gitattributes` and `.gitignore` and `audit/flow-install.json`, reinstalls the three git hooks, and touches nothing else:

```
python fusebase-flow-6.0.0-m6/maintainer/flow.py install --target <your-project> --providers <the providers audit/flow-install.json lists>
```

If you edited `policies/approval-policy.yml`, the re-run keeps your copy, which has no `gate_rounds`; the gate then allows 2 rounds, the shipped value. A module-size baseline that holds rows of your own (`policies/module-size-baseline.txt`) gets the core's rows back, and your rows move to `policies/module-size-baseline.project.txt`, your own file from then on; the 5.x core's row `821 hooks/local/upgrade.sh` goes. Add `--register-reader` to schedule the heartbeat reader every 5 minutes (`schtasks` on Windows, crontab elsewhere): it writes your crontab only after `crontab -l` exits 0 or says there is no crontab yet, adds no second line for the same project, and refuses a `schtasks` command over 261 characters; when it refuses or fails it prints the line to add by hand, and the install still exits 0. `--wire-hooks` merges Flow's two tool handlers into `.claude/settings.json` and `.codex/hooks.json` beside the CLI's entries, which it never changes; a plain install writes neither file. An upgrade needs no `--wire-hooks`: the wiring you have stays as it is, and a reader task you disabled stays disabled (see the two step-by-step sections below). Commit the result as the protected commit `workflows/lifecycle.md` describes: stage it by name, mint with `FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh` (the default 15 minutes can run out during a slow pre-commit), commit with a `flow:` subject, such as `flow: upgrade Fusebase Flow 6.0.0-m5 to 6.0.0-m6`, then run the same script with `--consume`. A `flow:` commit needs no task, so it also goes through in a project that already has a plan; it passes only when every staged path is a Flow file with the bytes `audit/flow-install.json` records, one of the four documents, or a change inside Flow's marked block in `AGENTS.md`, `CLAUDE.md`, `.gitattributes` or `.gitignore`. Then check it, read-only: `python fusebase-flow-6.0.0-m6/maintainer/flow.py health --target <your-project>` exits 0 when the install is healthy.

**Editing a protected Flow file with the hooks wired.** With Claude Code's tool hooks wired, an agent's Edit or Write of a Flow file (`policies/validator-free-paths.yml`, say) is denied unless an approval covers it, and the approval minted after staging cannot exist before the edit. Now one go-ahead covers both: when the operator says go in chat for the files named, the agent runs `FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh --paths <file>...` before the edit, edits those files, commits exactly them under a task's `T<n>`, then runs the same script with `--consume`. The approval names the files and the commit `HEAD` is at, covers Flow's own files only (never a CI workflow), lasts 30 minutes at most, writes an audit line at each use, and allows no other file and no commit that stages any other path; the commit that lands on that `HEAD` spends it, and moving `HEAD` back (`git reset --soft`, a branch or a detached `HEAD` there) does not revive it. Minting after staging works as before.

**One commit at a time.** The planner and the builders share one work tree and one git index. Every commit, the planner's and the builders', goes through `python hooks/local/commit.py -m "<subject>" <files>`: it waits while another such commit, or a git process holding the index, has the repository, stages exactly the files named and commits only them, so a planner commit during a builder run neither fails on `.git/index.lock` nor takes a builder's staged files. A file you deleted or renamed with `git rm` or `git mv` is named like any other; names are literal (`app[id].ts` is that one file) and a folder is refused. An `.git/index.lock` over two minutes old while no git process runs is named for you to remove, rather than waited on.

**Open branches and worktrees.** Git keeps one set of hooks for a whole repository, so the 6.0 hooks run on every branch and in every worktree as soon as one branch installs or migrates. `install` and `migrate` list the other local branches and linked worktrees that do not carry Flow 6.0 yet. On such a branch an ordinary commit is refused with a message that names the migrated branch: merge it in first (`git merge <the migrated branch>`), then commit. The FuseBase CLI's two update checkpoints still commit there, without lint and typecheck. Do this for each branch and worktree in the list before its next commit; a release or hotfix branch gets the whole migration with that merge. `git log --all --oneline --grep='^flow: migrate'` finds the migration commit, and `git branch -a --contains <that commit>` the branches that hold it.

**Start a fresh agent session.** After migrating or upgrading, close the agent sessions that were open and start new ones: a session keeps the rules it loaded when it started, so an open one goes on following 5.x's (or the previous release's).

**Commit subjects.** `commit-msg` takes exactly one `T<n>` in the subject, a task of `docs/flow/phases.md` at HEAD once that file has tasks; `plan:` and `ship:` only on the files the plan and ship skills name; `flow:` only on Flow's own files, for Flow's install, migration and upgrade commits; a merge by git's state. The FuseBase CLI's two update checkpoints, `chore(update): pre app update (<date>)` and `chore(update): post app update (<date>)`, pass whatever they stage, so `fusebase update` can commit them: `exempt_subjects` in `policies/evidence-classes.yml` names them, and only the committed file counts. If you edited that file, the re-run keeps your copy without the key; copy the key from the release's file. A commit outside the trivial tier (`policies/evidence-classes.yml`, empty by default) needs its task's backlog item.

**Lint and typecheck.** Git runs the pre-commit before the commit message exists, so Flow 6.0 runs your project's lint and typecheck in `commit-msg`, after the subject check, whenever the `commit-msg` git runs is Flow's (with a hook manager such as Husky in `core.hooksPath`, they stay in the pre-commit): a commit with a task still runs them and is refused when they fail. The two CLI checkpoints skip them and print a warning saying they were not run; run them yourself after `fusebase update`. A merge runs neither, as before. Flow's own records under `state/` (gate reports, flag rulings, run indexes, deploy lines) skip them with no declaration, except files whose extension a lint covers (`.json`, `.mjs` and the other code extensions); a glob you declare in `policies/validator-free-paths.yml` that matches such files prints a warning on each commit.

**Evidence rows.** A row whose earlier run of the same phase recorded a FAIL (FLAKY) passes only when its note cites an owner answer `A<n>` that `docs/flow/backlog.md` has under `## Answers`, or states `reproduced <k>/<n>` and cites each of those n runs by id; "repro" or "not reproduced" alone no longer does. The pre-commit's evidence check shows a row you recorded as FAIL, or BLOCKED without an accepted answer, as written ("holds as written"), never as PASS, and still lets the commit through. A live run starts after the deploy it checks has finished, except a pre-deploy baseline run, named so in its run-log title (`# Live run baseline-<run> <id> (<env>)`), which may start before the deploy it serves. `gate.py` counts only ledger records (lines that start with their time), never a `## Next` or `## Handoff` bullet that says "review"; a criterion that names its own phase's gate is still refused before dispatch, but a slice's gate (`P6-S1`), another phase's and "before the P6 gate" are not.

**New project:** the same install command with the providers you want, such as `--providers claude,codex`, at the top level of a git repository's main worktree.

**Project on Flow 5.x.** First run the dry run. It prints what it would remove, replace and add, what it never touches, and the open branches and worktrees above, and changes nothing. The dry run runs the structural preflight; `--apply` runs the project's lint and typecheck before any change; so a dry run that exits 0 means the migration will go through only once those two also pass by hand. Then run the migration, from the main worktree:

```
python fusebase-flow-6.0.0-m6/maintainer/flow.py migrate --target <your-project> --providers claude,codex
python fusebase-flow-6.0.0-m6/maintainer/flow.py migrate --target <your-project> --providers claude,codex --apply --go-ahead
```

`--apply` first checks everything that could stop it, and changes nothing if a check fails. It copies every file it removes or replaces into `.flow-migrate-<UTC time>/`. The migration lands as one commit, `flow: migrate Fusebase Flow <5.x version> to 6.0.0-m6`, through the new git hooks, and writes the Flow `.gitignore` block. It also removes the 5.x repair backups (`*.pre-flow-repair`, `*.pre-flow-repair.<n>`) left under `.claude/`, `.agents/` and `.codex/` whose file goes with the migration or is already gone; a folder that holds its own `.git` (a worktree under `.claude/worktrees/`, a submodule) is another checkout, and nothing in it is touched. Its report, at the top of `docs/flow/ledger.md`, ends with the health check to run after that commit and with what to do next: carry the open 5.x work into `docs/flow/` with the plan skill, one backlog item per evidence row, and keep the gate as your own step, never a builder's task.

**Undo.** The end of `--apply` and the migration report in `docs/flow/ledger.md` print this block with the values filled in. Paste it into Git Bash at the project's top level, as one unit. It checks out the pre-migration commit on a new branch, puts the 5.x git hooks back and restores the untracked files the migration removed or overwrote, from the backup folder. If that folder is gone, the block takes the hooks from the 5.x tree's `hooks/git/` and says so, and those untracked files cannot be restored; if that tree has no `hooks/git/` copies either, it stops before anything changes. It stops at the first step that fails, and your shell stays open. The branch you migrated keeps the migration commit.

```
( set -e
  if [ -d ".flow-migrate-<UTC time>" ]; then :; elif git cat-file -e "<the pre-migration commit>:hooks/git/pre-commit" 2>/dev/null && git cat-file -e "<the pre-migration commit>:hooks/git/commit-msg" 2>/dev/null && git cat-file -e "<the pre-migration commit>:hooks/git/pre-push" 2>/dev/null; then echo "NOTE: the backup folder .flow-migrate-<UTC time>/ is gone: the git hooks come from the 5.x tree's hooks/git/, and the untracked files the migration removed or overwrote cannot be restored"; else echo "STOPPED before any change: the backup folder .flow-migrate-<UTC time>/ is gone, and the pre-migration commit does not hold all three of hooks/git/pre-commit, commit-msg and pre-push to put the 5.x git hooks back from"; false; fi
  git checkout -b flow-5x-<UTC time> <the pre-migration commit>
  for h in pre-commit commit-msg pre-push; do if [ -f ".flow-migrate-<UTC time>/.git-hooks/$h" ]; then cp -p -- ".flow-migrate-<UTC time>/.git-hooks/$h" "$(git rev-parse --git-common-dir)/hooks/$h"; elif [ -d ".flow-migrate-<UTC time>" ]; then rm -f -- "$(git rev-parse --git-common-dir)/hooks/$h"; else git cat-file blob "<the pre-migration commit>:hooks/git/$h" > "$(git rev-parse --git-common-dir)/hooks/$h"; chmod +x -- "$(git rev-parse --git-common-dir)/hooks/$h"; fi; done
  if [ -d ".flow-migrate-<UTC time>" ]; then while IFS= read -r p; do mkdir -p -- "$(dirname -- "$p")"; cp -p -- ".flow-migrate-<UTC time>/$p" "$p"; done < ".flow-migrate-<UTC time>/.migrate/untracked.txt"; fi
)
```

## Upgrading a 6.0.0-m4 project to 6.0.0-m6 in one step

Both live projects take this today, from 6.0.0-m4 straight to 6.0.0-m6; 6.0.0-m5's changes come with it. Run these in Git Bash (any terminal elsewhere), in the folder that holds your project's folder; `<your-project>` is that folder's name. Start from a clean tree: commit or stash your own work first, and close the agent sessions open on the project (a session keeps the rules it loaded). The same lines serve every 6.0.0-m4 install: one with no tool hooks wired, one with Claude Code alone wired, and one with Claude Code and Codex wired. On the install line, give the providers your install already has: `audit/flow-install.json` lists them under `providers` (both live projects have `claude,codex`). Leave `--wire-hooks` off: the wiring in `.claude/settings.json` and `.codex/hooks.json` stays as it is, since Flow's entries did not change from 6.0.0-m4, and `--wire-hooks` with `claude,codex` would add a `.codex/hooks.json` a Claude-only wiring never had.

```
git clone --depth 1 --branch 6.0.0-m6 https://github.com/fusebase-dev/fusebase-flow.git fusebase-flow-6.0.0-m6
<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m6/hooks/requirements.txt
python fusebase-flow-6.0.0-m6/maintainer/flow.py install --target <your-project> --providers <the providers audit/flow-install.json lists>
cd <your-project>
git status --short
git add -u
git add -- hooks/local/commit.py hooks/local/lib/evidence_rules.py hooks/local/lib/rounds.py
if [ -f policies/module-size-baseline.project.txt ]; then git add -- policies/module-size-baseline.project.txt; fi
FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh
git commit -m "flow: upgrade Fusebase Flow 6.0.0-m4 to 6.0.0-m6"
bash hooks/local/write-bootstrap-approval.sh --consume
cd ..
python fusebase-flow-6.0.0-m6/maintainer/flow.py health --target <your-project>
```

What each step shows, as on the copy these steps were tested on (Onboarding migrated by 6.0.0-m4, Claude Code alone wired, a reader task registered and then disabled):
- the install lists `added:` with the three new Flow files above and, when your module-size baseline had rows of your own, `policies/module-size-baseline.project.txt`; your rows move there, and the 5.x core's row `821 hooks/local/upgrade.sh` goes; it lists the Flow files it replaced. Its line `provider hook wiring: not written` means it wrote no wiring this time; the wiring you have stays. Its line `heartbeat reader: registered earlier: <the recorded line>` (`not scheduled` when none is recorded) means it registered nothing this time; your task stays as it is. When other local branches or worktrees have no Flow 6.0 files, a WARNING names each one that must merge this branch before its next commit;
- `git status --short` lists ` M` lines, the Flow files the install changed, and `??` lines for the new files above. If it lists anything else, stop and set your own files aside without touching Flow's, for example with `git stash push -- <your files>`, then go on (a plain `git stash` would take Flow's changes too). `git add -u` stages the changed files, the next two lines the new ones;
- the commit runs the secret scan, the protected paths and the module size, then your lint and typecheck in `commit-msg`; it takes a few minutes on a large project, which the 30-minute mint covers;
- health ends `HEALTH: healthy` and exits 0; for an install with Claude Code alone wired it shows `wiring: claude wired` and `wiring: codex unenforced`. Its reader line now says what the scheduler says: a task you disabled reads `the task is Disabled`, and health stays healthy.

After the upgrade, a PASS row that 6.0.0-m4 accepted with a FLAKY note such as `repro …` holds only when its note states `reproduced <k>/<n>` citing each of those runs, or cites an owner answer `A<n>`: the pre-commit's evidence check refuses the first commit that stages that phase's evidence file until the note says so.

In a wired Claude Code session, the steps inside the project (`git status --short`, the three `git add` lines, the mint, the commit, `--consume` and `cd ..`) go through the project's own `hooks/handlers/pre_tool_use.py`, which allows each of them; the agent mints only on the operator's go-ahead in chat. Outside the project folder that handler stops with an error (it cannot find the project's git root) without blocking the command, so run the clone, the install and health in a terminal.

**The reader task.** The upgrade leaves the reader task as it is: a task you disabled stays disabled. 6.0.0-m6's reader starts git with no console window, so the window that opened every 5 minutes is gone. To turn the reader back on, re-run the install with `--register-reader` after the upgrade commit, from the same folder: `python fusebase-flow-6.0.0-m6/maintainer/flow.py install --target <your-project> --providers <the providers audit/flow-install.json lists> --register-reader`. On Windows it runs `schtasks /Create /F` for the same task name, which replaces your task, enabled, running `pythonw.exe` (found beside this Python, through the py launcher or on PATH); on Linux and macOS it adds no second crontab line. It changes no Flow file. `audit/flow-install.json` records the line it registers: when `git status --short` in the project then lists that file, the line differs from the one recorded before, so commit it alone (`git add -- audit/flow-install.json`, then `git commit -m "flow: register the Flow reader"`; the manifest alone needs no mint); when it lists nothing, as on the copy these steps were tested on (6.0.0-m4 had already registered `pythonw.exe`), the line was recorded already and there is nothing to commit. Health then reads `the task is Ready`.

## What is new

| Piece | What it does |
|---|---|
| `write-bootstrap-approval.sh --paths <file>...`, `path_policy.py`, `pre_tool_use.py` | One go-ahead, minted before the edit, names the Flow files and the commit `HEAD` is at: the wired PreToolUse handler allows an Edit or Write of those files and no other, the pre-commit allows a commit whose staged paths are all named, and the commit that lands spends it. 1 to 30 minutes (`FF_BOOTSTRAP_TTL_MIN`); a hand-made one with a longer life, a glob or a path of another category is refused; each mint and each use writes an audit line. The repo-relative path the handler checks is written with `/` on Windows too |
| The pre-commit's trusted check | Copies HEAD's `audit_logger.py` beside the protected-path enforcer (never as a sentinel), so a commit's use of a go-ahead is audited |
| `validate_evidence.py`, the flaky check | Counts only earlier runs whose folder sits beside the row's run (the phase's smoke root): another phase's runs that an index carries no longer make a row FLAKY |
| `gate.py` | A slice's PASS line dispatches its review reader; a phase's, its two skeptics, then the verdict, as `workflows/lifecycle.md` says. It counts `review <slice>` records beside the `verdict` records, each against `gate_rounds`, and either one at the limit is `BLOCKED-AT-gate-budget` |
| `templates/ledger.md` | A `review <slice>` record kind, with `result=` PASS or FAIL and `agent=` the reader agent id |
| The pre-commit and `commit-msg`, the stage times | Each stage's time also goes to `state/audit/commit-stages.tsv` (gitignored): time, parent commit, hook, stage, seconds; only where `state/` exists |
| `post_tool_use.py`, `checks.py` | Every tool-call audit line carries its `agent_id`; `checks.py` logs the planner's own calls (no `agent_id`) in a slice's window, from the audit line, where a provider's hooks write it |
| `hooks/local/commit.py` | One commit at a time per repository, with only the files named (`git commit --only`): it waits for another Flow commit or a git index lock, up to 30 minutes, then exits 3 having changed nothing |
| `slice.py` | An item whose criterion or test names its own phase's gate (`P6 gate`, `phase 6's gate`, `state/gate/P6.txt`) prints `BLOCKED-AT-criterion` and exits 3, so the slice is not dispatched |
| `flow.py health`, the reader | Asks the scheduler, read-only (`schtasks /Query`, `crontab -l`): the task is Ready, Running or Disabled, deleted, or out of the crontab |
| `validator_tier.py` | Flow's records under `state/` skip lint and typecheck with no declaration, except files with an extension a lint covers; a declared glob matching such files at HEAD prints a WARNING |
| `module_size.py`, `policies/module-size-baseline.project.txt` | The project's rows live in their own committed, protected file, read beside Flow's; `--write-baseline` writes only that file; install moves a project's rows there and drops the 5.x core's `upgrade.sh` row; health never checks the project's file |
| `flow.py migrate` | Removes the orphan 5.x repair backups under `.claude/`, `.agents/` and `.codex/`, backed up and listed; its report and output end with what to do next: one backlog item per evidence row, the gate the planner's step |
| `hooks/local/lib/rounds.py`, `hooks/local/lib/evidence_rules.py` (new) | The gate's round accounting and the evidence validator's run-log, FINDING and FLAKY rules, moved out of `gate.py` and `validate_evidence.py` unchanged, so neither passes its line ceiling |
| The gate's round count (review fix) | Counts only ledger records, lines that start with their time; a `## Next` or `## Handoff` bullet that says "review P1-S1" is no round |

## Limits

- Codex: unproven. `--wire-hooks` writes `.codex/hooks.json`, and Codex asks you to trust each project hook before it runs one; no slice has run on Codex yet. Codex reports edits as `apply_patch`, which the handlers do not parse, so the tool-time path and secret checks are unenforced there; the git pre-commit covers both. `docs/provider-coverage.md` lists each element.
- `state/status.line` says a provider is `wired` when its settings name a Flow handler that exists; that proves no Codex run.
- A go-ahead is spent by any commit that lands after it, a builder's too, and stays spent: the agent then asks again. An Edit refused because another staged path is not named reads as the plain FR-07 refusal.
- `maintainer/flow.py` and `health.py`, run in a terminal, start their processes without `CREATE_NO_WINDOW`; only the files under `hooks/` and the git hooks carry it.
- A pre-deploy baseline run is known by the word `baseline` in its run-log title; nothing checks that it really ran before the deploy.
- `reproduced <k>/<n>` is counted from the run ids the note cites, against the phase's run index; whether those runs recorded the row is not checked.
- A commit made with plain `git commit` (a person, the FuseBase CLI's checkpoints) takes no Flow commit lock; `commit.py` still waits for its index lock and never takes its staged files.
- The planner's tool calls are counted from the audit line, so only where a provider's hooks are wired; Codex: unproven.
- `gate.py` does not print the commit stage times; they are read from `state/audit/commit-stages.tsv`.
- A criterion that depends on its own phase's gate without naming it is not caught.
- Health reads the reader's state in English `schtasks` output; another language prints that the answer could not be read.
- `hooks/local/check-module-size.sh --write-baseline` still prints `chore(fr25): adopt module-size baseline`, which the new `commit-msg` rejects: commit the adoption under a task's `T<n>`. That script is kernel text and changes on 5.x first.
- Lint and typecheck print their lines with the `[fusebase-flow:pre-commit]` prefix even when `commit-msg` runs them: that text is kernel, shared with 5.x.
- What the terminal shows for a blocked push is unchanged: the pre-push still prints the push URL as git gave it; only the audit log drops its userinfo.
- `hooks/local/install-git-hooks.sh` run by hand in a linked worktree still writes the shared hooks; `flow.py install` refuses there.
- A delete mint run any other way (an absolute path to the script, an environment prefix, `bash -c`, the action quoted) gets no exemption and is refused as before; so is every other action's mint whose `--command` text a rule gates, such as a deploy or a push to main: an agent asks the operator to run that one in a terminal.
- The two CLI checkpoints commit with lint and typecheck red; `FLOW_RULES.md` rule 6 does not name that exception yet.
- The adversarial review's findings M6-1 to M6-14 and M6-26 to M6-28 wait for the owner's order; none is in this release.

This is a pre-release. CI gates it on Linux; the Windows (Git Bash) run reports but gates nothing until 6.0.0.
