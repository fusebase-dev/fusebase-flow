# 6.0.0-m7: the tool-time path check, the 5.x line-ending pins, merges and pushes checked, true health, local overrides that only tighten (pre-release)

The Fusebase Flow 6.0 core with the first five items of the owner's m7 list: the tool-time protected-path check judges the path git names, whatever spelling the tool sends (an 8.3 short name, `..`, `./`, a symlink, NotebookEdit's notebook path); the 5.x folder-wide `text eol=lf` lines that damaged binaries committed under them are removed by the migration and by the install; a new `pre-merge-commit` hook and a pre-push check of every commit the remote lacks stop a merge, cherry-pick, rebase or revert from carrying a secret or an unapproved protected-path change; health reads the folder git really runs hooks from, parses the wiring and lists the Flow files an install kept; and a gitignored `*.local.yml` override only ever tightens, while a shell write into `policies/` or `state/approvals/` is denied. Both live projects upgrade from 6.0.0-m6 in one step (see "Upgrading a 6.0.0-m6 project to 6.0.0-m7").

Needs git, bash and Python 3.10+ with PyYAML. The hooks and the two approval scripts run the first of `python3`, `python` and `py -3` that is 3.10+, so a Windows host with python.org's Python and no `python3` works too. PyYAML must be installed for that one, with its own pip: `<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m7/hooks/requirements.txt`, not a bare `pip`, which can belong to another Python. Get this release; the second line installs PyYAML:

```
git clone --depth 1 --branch 6.0.0-m7 https://github.com/fusebase-dev/fusebase-flow.git fusebase-flow-6.0.0-m7
<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m7/hooks/requirements.txt
```

That is usually `python3` on Linux and macOS; on Windows with python.org's Python it is `python` (`python -m pip install -r fusebase-flow-6.0.0-m7/hooks/requirements.txt`) or `py -3`. Windows' default App execution aliases make `python3` the Microsoft Store shortcut, which fails the 3.10+ check, so Flow goes on to `python` and `py -3`; when none of the three is Python 3.10+, the commit is refused until you turn off the python.exe and python3.exe App execution aliases (Settings, Apps, Advanced app settings) or install Python 3.10+.

**Project on 6.0.0-m6, or an earlier 6.0.0 pre-release.** Run the install from the project's main worktree (in a linked worktree, made by `git worktree add`, it refuses and names the main one). It adds the new files, replaces the Flow files you have not edited, keeps the ones you edited, rewrites its marked blocks in `.gitattributes` and `.gitignore` and `audit/flow-install.json`, removes Flow 5.x's line-ending pins from `.gitattributes`, reinstalls the git hooks, and touches nothing else:

```
python fusebase-flow-6.0.0-m7/maintainer/flow.py install --target <your-project> --providers <the providers audit/flow-install.json lists>
```

Add `--register-reader` to schedule the heartbeat reader every 5 minutes (`schtasks` on Windows, crontab elsewhere): it writes your crontab only after `crontab -l` exits 0 or says there is no crontab yet, adds no second line for the same project, and refuses a `schtasks` command over 261 characters; when it refuses or fails it prints the line to add by hand, and the install still exits 0. `--wire-hooks` merges Flow's two tool handlers into `.claude/settings.json` and `.codex/hooks.json` beside the CLI's entries, which it never changes; a plain install writes neither file. An upgrade needs no `--wire-hooks`: the wiring you have stays as it is, and a reader task stays as it is. Commit the result as the protected commit `workflows/lifecycle.md` describes: stage it by name, mint with `FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh` (the default 15 minutes can run out during a slow pre-commit), commit with a `flow:` subject, such as `flow: upgrade Fusebase Flow 6.0.0-m6 to 6.0.0-m7`, then run the same script with `--consume`. A `flow:` commit needs no task, so it also goes through in a project that already has a plan; it passes only when every staged path is a Flow file with the bytes `audit/flow-install.json` records, one of the four documents, or a change inside Flow's marked block in `AGENTS.md`, `CLAUDE.md`, `.gitattributes` or `.gitignore` (in `.gitattributes`, also the removal of Flow 5.x's pins). Then check it, read-only: `python fusebase-flow-6.0.0-m7/maintainer/flow.py health --target <your-project>` exits 0 when the install is healthy.

**The tool-time path check.** With Claude Code's tool hooks wired, an Edit, Write or NotebookEdit of a protected file is judged by the path git names: the handler resolves the edited path (from the session's folder when it is relative) and the project's folder before comparing them, so an 8.3 short name (`C:\Users\RUNNER~1\...`), another case, `..`, `./`, a junction or a symlink inside the project reaches the protected check. Before, any of those spellings made the comparison fail and the edit was allowed (the commit-time check still refused it).

**Line endings.** Flow 5.x projects carry folder-wide `text eol=lf` lines in `.gitattributes` outside Flow's marked block (`hooks/**`, `templates/**`, `state/**`, `workflows/**`, `agents/**`, `policies/**`, `.agents/skills/**`, `.codex/agents/**`, `.claude/commands/**` and others). git treats a binary committed under them as text and rewrites its CRLF bytes: a PNG loses a byte and its signature breaks, in the repository and in every clone. The migration's dry run lists them and `--apply` removes them (the file is backed up first); the install removes them on an upgrade and names each line it removed. Your own lines stay: extension rules such as `*.sql text eol=lf` or `*.png binary`, a pin of your own folder, a 5.x copy of Flow's extension rules. 6.0's own block pins exact paths only. A binary committed before the upgrade under those folders keeps the bytes git stored then; commit it again after the upgrade to store it whole.

**Merges and pushes.** git runs no pre-commit for a merge it completes on its own, a cherry-pick, a rebase's replays or a revert, so a secret or a protected-path change committed with `--no-verify` on one branch could reach the remote by any of them. Now:
- the new `pre-merge-commit` git hook checks what a merge brings in: the secret patterns, and each protected-path change, which must be on record; files whose merged bytes a remote-tracking branch already holds came from the remote and are not judged. A refused merge stays in progress: `git merge --abort` drops it.
- the pre-push checks every commit the remote lacks the same way (`hooks/local/lib/range_check.py`).
- "on record": each protected-path change the pre-commit (or `pre-merge-commit`) allowed is written by `commit-msg` to `.git/flow/approved-changes.tsv`, one file for all worktrees. A change passes when recorded steps lead from its old bytes to its new ones, so an amend or a squash of approved commits passes and a revert does not; a `flow:` commit of Flow's own files passes as it did at commit time.
- not judged: commits a remote-tracking branch holds, and the history from before this check (commits whose tree, and whose parents' trees, have no `hooks/git/pre-merge-commit`), so the first push after the upgrade checks only what the upgrade and later commits carry.
- a refused push names the commit and what it carries. A secret: rotate it and rewrite the branch without it. A protected-path change the operator approves (a cherry-pick of an approved change onto another base, a rebase that merged two changes to the same protected file): the agent runs `python hooks/local/lib/range_check.py --record-commit <sha>` on the operator's go-ahead in chat, then pushes again. An approved protected change on a branch the remote lacks merges through `git merge --no-commit <branch>`, the mint, `git commit`, then `--consume`.

**Health.** `flow.py health` reads the git hooks in the folder git runs them from (`git rev-parse --git-path hooks`): with `core.hooksPath` pointing elsewhere (Husky writes it) no Flow hook runs, and health says `NOT healthy` and names both folders; the install prints a WARNING then and still writes Flow's hooks only to the common git folder's `hooks/`, never into the hook manager's. Wiring is read by parsing `.claude/settings.json` and `.codex/hooks.json`: `wired` needs a `PreToolUse` entry whose command names `hooks/handlers/pre_tool_use.py`; a file that only mentions a handler reads `unenforced`. A Flow file the install kept because you edited it is recorded as kept and listed `kept, not current`; a kept file under `hooks/` is `NOT healthy`, as a changed one is.

**Local overrides.** A gitignored `policies/*.local.yml` only ever tightens: it may add deny and approval rules, protected paths and secret patterns, lower a TTL or `gate_rounds`, and turn `strict_approvals` on; it never removes, replaces or weakens a shipped entry, and anything else it holds is ignored (a local `allow`, `default`, `whitelist`, `workflow_mode`, `exempt_globs`). What a project loosens belongs in a committed, protected file: its own over-ceiling files in `policies/module-size-baseline.project.txt`, a workflow mode or a TTL in the committed policy (an edit of a Flow file, which the install then keeps). A shell write into `policies/`, `state/approvals/` or `.git/flow/` (redirection, `tee`, `cp`/`mv`/`install`/`ln`/`rsync` into them, `sed -i`, a script that opens a file there for writing, PowerShell's `Set-Content` and its kin) is denied at tool time; reading them stays open, and Flow's own scripts (the two mints, `check-module-size.sh --write-baseline`) write there as before.

**Editing a protected Flow file with the hooks wired.** With Claude Code's tool hooks wired, an agent's Edit or Write of a Flow file (`policies/validator-free-paths.yml`, say) is denied unless an approval covers it, and the approval minted after staging cannot exist before the edit. Now one go-ahead covers both: when the operator says go in chat for the files named, the agent runs `FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh --paths <file>...` before the edit, edits those files, commits exactly them under a task's `T<n>`, then runs the same script with `--consume`. The approval names the files and the commit `HEAD` is at, covers Flow's own files only (never a CI workflow), lasts 30 minutes at most, writes an audit line at each use, and allows no other file and no commit that stages any other path; the commit that lands on that `HEAD` spends it, and moving `HEAD` back (`git reset --soft`, a branch or a detached `HEAD` there) does not revive it. Minting after staging works as before.

**One commit at a time.** The planner and the builders share one work tree and one git index. Every commit, the planner's and the builders', goes through `python hooks/local/commit.py -m "<subject>" <files>`: it waits while another such commit, or a git process holding the index, has the repository, stages exactly the files named and commits only them, so a planner commit during a builder run neither fails on `.git/index.lock` nor takes a builder's staged files. A file you deleted or renamed with `git rm` or `git mv` is named like any other; names are literal (`app[id].ts` is that one file) and a folder is refused. An `.git/index.lock` over two minutes old while no git process runs is named for you to remove, rather than waited on.

**Open branches and worktrees.** Git keeps one set of hooks for a whole repository, so the 6.0 hooks run on every branch and in every worktree as soon as one branch installs or migrates. `install` and `migrate` list the other local branches and linked worktrees that do not carry Flow 6.0 yet. On such a branch an ordinary commit is refused with a message that names the migrated branch: merge it in first (`git merge <the migrated branch>`), then commit. The FuseBase CLI's two update checkpoints still commit there, without lint and typecheck. Do this for each branch and worktree in the list before its next commit; a release or hotfix branch gets the whole migration with that merge. `git log --all --oneline --grep='^flow: migrate'` finds the migration commit, and `git branch -a --contains <that commit>` the branches that hold it.

**Start a fresh agent session.** After migrating or upgrading, close the agent sessions that were open and start new ones: a session keeps the rules it loaded when it started, so an open one goes on following 5.x's (or the previous release's).

**Commit subjects.** `commit-msg` takes exactly one `T<n>` in the subject, a task of `docs/flow/phases.md` at HEAD once that file has tasks; `plan:` and `ship:` only on the files the plan and ship skills name; `flow:` only on Flow's own files, for Flow's install, migration and upgrade commits; a merge by git's state. The FuseBase CLI's two update checkpoints, `chore(update): pre app update (<date>)` and `chore(update): post app update (<date>)`, pass whatever they stage, so `fusebase update` can commit them: `exempt_subjects` in `policies/evidence-classes.yml` names them, and only the committed file counts. If you edited that file, the re-run keeps your copy without the key; copy the key from the release's file. A commit outside the trivial tier (`policies/evidence-classes.yml`, empty by default) needs its task's backlog item.

**Lint and typecheck.** Git runs the pre-commit before the commit message exists, so Flow 6.0 runs your project's lint and typecheck in `commit-msg`, after the subject check, whenever the `commit-msg` git runs is Flow's (with a hook manager such as Husky in `core.hooksPath`, they stay in the pre-commit): a commit with a task still runs them and is refused when they fail. The two CLI checkpoints skip them and print a warning saying they were not run; run them yourself after `fusebase update`. A merge runs neither, as before. Flow's own records under `state/` (gate reports, flag rulings, run indexes, deploy lines) skip them with no declaration, except files whose extension a lint covers (`.json`, `.mjs` and the other code extensions); a glob you declare in `policies/validator-free-paths.yml` that matches such files prints a warning on each commit.

**Evidence rows.** A row whose earlier run of the same phase recorded a FAIL (FLAKY) passes only when its note cites an owner answer `A<n>` that `docs/flow/backlog.md` has under `## Answers`, or states `reproduced <k>/<n>` and cites each of those n runs by id; "repro" or "not reproduced" alone no longer does. The pre-commit's evidence check shows a row you recorded as FAIL, or BLOCKED without an accepted answer, as written ("holds as written"), never as PASS, and still lets the commit through. A live run starts after the deploy it checks has finished, except a pre-deploy baseline run, named so in its run-log title (`# Live run baseline-<run> <id> (<env>)`), which may start before the deploy it serves. `gate.py` counts only ledger records (lines that start with their time), never a `## Next` or `## Handoff` bullet that says "review"; a criterion that names its own phase's gate is still refused before dispatch, but a slice's gate (`P6-S1`), another phase's and "before the P6 gate" are not.

**New project:** the same install command with the providers you want, such as `--providers claude,codex`, at the top level of a git repository's main worktree.

**Project on Flow 5.x.** First run the dry run. It prints what it would remove, replace and add, what it never touches, and the open branches and worktrees above, and changes nothing. The dry run runs the structural preflight; `--apply` runs the project's lint and typecheck before any change; so a dry run that exits 0 means the migration will go through only once those two also pass by hand. Then run the migration, from the main worktree:

```
python fusebase-flow-6.0.0-m7/maintainer/flow.py migrate --target <your-project> --providers claude,codex
python fusebase-flow-6.0.0-m7/maintainer/flow.py migrate --target <your-project> --providers claude,codex --apply --go-ahead
```

`--apply` first checks everything that could stop it, and changes nothing if a check fails. It copies every file it removes or replaces into `.flow-migrate-<UTC time>/`. The migration lands as one commit, `flow: migrate Fusebase Flow <5.x version> to 6.0.0-m7`, through the new git hooks, and writes the Flow `.gitignore` block. It also removes the 5.x repair backups (`*.pre-flow-repair`, `*.pre-flow-repair.<n>`) left under `.claude/`, `.agents/` and `.codex/` whose file goes with the migration or is already gone; a folder that holds its own `.git` (a worktree under `.claude/worktrees/`, a submodule) is another checkout, and nothing in it is touched. Flow 5.x's line-ending pin lines go from `.gitattributes` (the dry run lists them). Its report, at the top of `docs/flow/ledger.md`, ends with the health check to run after that commit and with what to do next: carry the open 5.x work into `docs/flow/` with the plan skill, one backlog item per evidence row, and keep the gate as your own step, never a builder's task.

**Undo.** The end of `--apply` and the migration report in `docs/flow/ledger.md` print this block with the values filled in. Paste it into Git Bash at the project's top level, as one unit. It checks out the pre-migration commit on a new branch, puts the 5.x git hooks back and restores the untracked files the migration removed or overwrote, from the backup folder. If that folder is gone, the block takes the hooks from the 5.x tree's `hooks/git/` and says so, and those untracked files cannot be restored; if that tree has no `hooks/git/` copies either, it stops before anything changes. It stops at the first step that fails, and your shell stays open. The branch you migrated keeps the migration commit.

```
( set -e
  if [ -d ".flow-migrate-<UTC time>" ]; then :; elif git cat-file -e "<the pre-migration commit>:hooks/git/pre-commit" 2>/dev/null && git cat-file -e "<the pre-migration commit>:hooks/git/commit-msg" 2>/dev/null && git cat-file -e "<the pre-migration commit>:hooks/git/pre-push" 2>/dev/null; then echo "NOTE: the backup folder .flow-migrate-<UTC time>/ is gone: the git hooks come from the 5.x tree's hooks/git/, and the untracked files the migration removed or overwrote cannot be restored"; else echo "STOPPED before any change: the backup folder .flow-migrate-<UTC time>/ is gone, and the pre-migration commit does not hold all three of hooks/git/pre-commit, commit-msg and pre-push to put the 5.x git hooks back from"; false; fi
  git checkout -b flow-5x-<UTC time> <the pre-migration commit>
  for h in pre-commit commit-msg pre-push; do if [ -f ".flow-migrate-<UTC time>/.git-hooks/$h" ]; then cp -p -- ".flow-migrate-<UTC time>/.git-hooks/$h" "$(git rev-parse --git-common-dir)/hooks/$h"; elif [ -d ".flow-migrate-<UTC time>" ]; then rm -f -- "$(git rev-parse --git-common-dir)/hooks/$h"; else git cat-file blob "<the pre-migration commit>:hooks/git/$h" > "$(git rev-parse --git-common-dir)/hooks/$h"; chmod +x -- "$(git rev-parse --git-common-dir)/hooks/$h"; fi; done
  if [ -d ".flow-migrate-<UTC time>" ]; then while IFS= read -r p; do mkdir -p -- "$(dirname -- "$p")"; cp -p -- ".flow-migrate-<UTC time>/$p" "$p"; done < ".flow-migrate-<UTC time>/.migrate/untracked.txt"; fi
)
```

## Upgrading a 6.0.0-m6 project to 6.0.0-m7

Both live projects take this, from 6.0.0-m6. Run these in Git Bash (any terminal elsewhere), in the folder that holds your project's folder; `<your-project>` is that folder's name. Start from a clean tree: commit or stash your own work first, and close the agent sessions open on the project (a session keeps the rules it loaded). The same lines serve every 6.0.0-m6 install: one with no tool hooks wired, one with Claude Code alone wired, and one with Claude Code and Codex wired. On the install line, give the providers your install already has: `audit/flow-install.json` lists them under `providers` (both live projects have `claude,codex`). Leave `--wire-hooks` off: the wiring in `.claude/settings.json` and `.codex/hooks.json` stays as it is, since Flow's entries did not change from 6.0.0-m6, and `--wire-hooks` with `claude,codex` would add a `.codex/hooks.json` a Claude-only wiring never had.

```
git clone --depth 1 --branch 6.0.0-m7 https://github.com/fusebase-dev/fusebase-flow.git fusebase-flow-6.0.0-m7
<the interpreter Flow will use> -m pip install -r fusebase-flow-6.0.0-m7/hooks/requirements.txt
python fusebase-flow-6.0.0-m7/maintainer/flow.py install --target <your-project> --providers <the providers audit/flow-install.json lists>
cd <your-project>
git status --short
git add -u
git add -- hooks/git/pre-merge-commit hooks/local/lib/eol_pins.py hooks/local/lib/range_check.py
FF_BOOTSTRAP_TTL_MIN=30 bash hooks/local/write-bootstrap-approval.sh
git commit -m "flow: upgrade Fusebase Flow 6.0.0-m6 to 6.0.0-m7"
bash hooks/local/write-bootstrap-approval.sh --consume
cd ..
python fusebase-flow-6.0.0-m7/maintainer/flow.py health --target <your-project>
```

What each step shows, as on the copy these steps were tested on (Onboarding migrated by 6.0.0-m4, upgraded to 6.0.0-m6 by its note, Claude Code alone wired, a reader task registered and Ready):
- the install lists `added:` with the three new Flow files above and `replaced:` the Flow files that changed (ten on the copy: `VERSION`, `hooks/git/commit-msg`, `hooks/git/pre-push`, `hooks/handlers/pre_tool_use.py`, `hooks/local/install-git-hooks.sh`, `hooks/local/lib/flow_owned.py`, `hooks/local/reader.py`, `hooks/shared/module_size.py`, `hooks/shared/policy_loader.py`, `policies/command-policy.yml`). A project migrated from Flow 5.x that still carries 5.x's line-ending pins (Onboarding does) also shows `merged: .gitattributes (block updated)` and `[flow] .gitattributes: removed 56 Flow 5.x line-ending pin lines`, then each line; a project's own lines are not listed and stay. Under `git hooks:` it shows `current pre-commit`, `installed commit-msg`, `installed pre-push` and `installed pre-merge-commit`. Its line `provider hook wiring: not written` means it wrote no wiring this time; the wiring you have stays. Its line `heartbeat reader: registered earlier: <the recorded line>` (`not scheduled` when none is recorded) means it registered nothing this time: your task stays as it is, an enabled one enabled. With `core.hooksPath` set it prints the WARNING described above. When other local branches or worktrees have no Flow 6.0 files, a WARNING names each one that must merge this branch before its next commit;
- `git status --short` lists ` M` lines, the Flow files the install changed (with `.gitattributes` and `audit/flow-install.json`), and `??` lines for the three new files. If it lists anything else, stop and set your own files aside without touching Flow's, for example with `git stash push -- <your files>`, then go on (a plain `git stash` would take Flow's changes too). `git add -u` stages the changed files, the next line the new ones;
- the commit runs the secret scan, the protected paths and the module size, then your lint and typecheck in `commit-msg`, which also puts the protected-path changes the commit carries on record for the push check; it takes a few minutes on a large project, which the 30-minute mint covers;
- health ends `HEALTH: healthy` and exits 0, now with `git hook: pre-merge-commit installed` beside the three; for an install with Claude Code alone wired it shows `wiring: claude wired` and `wiring: codex unenforced`, and its reader line still says what the scheduler says: `the task is Ready`.

In a wired Claude Code session, the steps inside the project (`git status --short`, the two `git add` lines, the mint, the commit, `--consume` and `cd ..`) go through the project's own `hooks/handlers/pre_tool_use.py`, which allows each of them; the agent mints only on the operator's go-ahead in chat. Outside the project folder that handler stops with an error (it cannot find the project's git root) without blocking the command, so run the clone, the install and health in a terminal.

**After the upgrade.** Health may now say what it did not before:
- `git hooks: core.hooksPath makes git run the hooks in <folder>, not the Flow hooks install writes to <.git/hooks>: ...` and `NOT healthy`: a hook manager (Husky) owns the hooks; until it calls Flow's, none of them runs. The install prints the same as a WARNING.
- `wiring: claude unenforced` or `wiring: codex unenforced` where it said `wired`: the settings file mentions a Flow handler but registers no `PreToolUse` command for `hooks/handlers/pre_tool_use.py`; re-run the install with `--wire-hooks` for that provider, or leave it unenforced.
- `kept, not current: <path> (your edit; ...)`: a Flow file you edited, which the install keeps and does not upgrade; under `hooks/` it makes health NOT healthy. Compare it with the release's copy and take the release's, or keep your edit knowingly.
And the first push after the upgrade runs the new range check over what the upgrade commit and later commits carry; your older history is not checked.

## Limits

- **The review of this release, for 6.0.0-m8:** a branch older than the upgrade is not range-checked; an octopus merge, and lines a combined diff marks other than `++`, skip the secret scan; remote-tracking branches of every remote are trusted, not only the push's; `--record-commit` is the operator's word with no audit line of its own; six more Windows spellings of a path pass the tool-time check; a project line written exactly like a 5.x pin is removed with them.
- **Not in this release, 6.0.0-m8's:** the rest of the adversarial review's causes in the owner's order (M6-7 the manifest-row forgery, M6-6 an expiry cap and single use for every approval category, M6-8 the MERGE_HEAD check, M6-9 unicode paths, M6-14 symlinked overlays, r3-83 the validator reading from the index, r1-28 the FINDING marker match, M6-11 the tag ruleset and post-publish re-check), the documentation items, and the eleven field items from the two projects' first day under 6.0.0-m6.
- The approval record is a file in `.git/flow/`: a shell write into it is denied at tool time, but a person, or a process the hooks do not see, can write a row, as with the audit log. A `flow:` commit is accepted by `flow_owned.py`, so the manifest-row forgery (M6-7, 6.0.0-m8) reaches the push check too.
- Each clone keeps its own record. A protected change made in another clone reaches yours through the remote, which the check does not judge; one fetched straight from a path or a URL with no remote-tracking branch is judged, and its push needs `--record-commit`.
- A rebase that replays an approved protected-path change onto a base where that file changed too, or a merge whose both sides changed the same protected file, makes a change nobody approved as such: the push or the merge is refused until the operator records it (`--record-commit`, or `git merge --no-commit`, the mint and `git commit`).
- `pre-merge-commit` sees what a merge brings into the index, not the commits it came from (git writes `MERGE_HEAD` after the hook runs); the pre-push judges those commits one by one.
- Health does not tell a hook manager that calls Flow's hooks (`.husky/pre-commit` running them) from one that does not: with `core.hooksPath` set it is NOT healthy either way.
- The tool-time deny of a shell write into `policies/` matches the command's text: a write by a script file, a variable or an alias is not seen, and a heredoc or a commit message that only mentions `> policies/...` is denied. The pre-commit's protected-path check still refuses the commit of such a change.
- Codex: unproven. `--wire-hooks` writes `.codex/hooks.json`, and Codex asks you to trust each project hook before it runs one; no slice has run on Codex yet. Codex reports edits as `apply_patch`, which the handlers do not parse, so the tool-time path and secret checks are unenforced there; the git hooks cover both. `docs/provider-coverage.md` lists each element.
- A go-ahead is spent by any commit that lands after it, a builder's too, and stays spent: the agent then asks again.
- `maintainer/flow.py` and `health.py`, run in a terminal, start their processes without `CREATE_NO_WINDOW`; only the files under `hooks/` and the git hooks carry it.
- Health reads the reader's state in English `schtasks` output; another language prints that the answer could not be read.
- `hooks/local/check-module-size.sh --write-baseline` still prints `chore(fr25): adopt module-size baseline`, which `commit-msg` rejects: commit the adoption under a task's `T<n>`.
- The two CLI checkpoints commit with lint and typecheck red; `FLOW_RULES.md` rule 6 does not name that exception yet.
- An edited `policies/evidence-classes.yml` that an upgrade keeps gets no new keys (O-26); it is read at HEAD only and has no local twin, so this release leaves it as it was.

This is a pre-release. CI gates it on Linux; the Windows (Git Bash) run reports but gates nothing until 6.0.0.
